# Sinal — handoff completo do projeto

Este documento existe pra te (ou a outra instância de IA que for mexer nisso) colocar 100% a par do projeto sem precisar reconstruir o histórico. Leia antes de tocar em qualquer coisa.

## 1. Por que esse projeto existe

Em agosto de 2026, a ANPD determinou que o Discord suspendesse compartilhamento de tela e vídeo no Brasil (voz e texto continuaram funcionando normalmente). O dono desse projeto joga com um grupo de amigos e usava o compartilhamento de tela do Discord pra assistir jogo/vídeo junto. Como alternativa, pediu pra eu construir uma ferramenta própria de compartilhamento de tela, pra usar **em paralelo** com a call de voz do Discord (que continua sendo usada normalmente pra conversar — o app só cuida da parte visual).

**Não é (e não deve virar) um clone do Discord.** É uma ferramenta bem pontual, pra um grupo pequeno de amigos, sem conta de usuário pros amigos, sem persistência de dados.

## 2. Stack e princípio de arquitetura

- **Frontend estático sem build step**: `index.html` (marcação), `style.css` e `app.js` — três arquivos simples, sem framework, sem bundler, sem npm. Era um `index.html` único até a v0.7.1; separado na v0.8.0 a pedido do usuário (achava o arquivo único confuso demais de mexer).
- **Transporte de vídeo/áudio: [LiveKit](https://livekit.io/) self-hosted numa VM da Oracle Cloud (Always Free)**. Desde a v0.8.0 (2026-08-24), **não é mais P2P/malha** — era PeerJS puro antes disso (ver §11 pra motivo da troca). De 2026-08-24 até 2026-08-28 rodou no **LiveKit Cloud** (SFU gerenciado); migrado pra self-host depois de bater o limite mensal real do plano free (ver §12, "Migração pro self-host") — o servidor é o mesmo LiveKit, o SDK/protocolo não muda, só quem hospeda.
- **Backend**: `api/get-token.js` (gera o token de acesso do LiveKit) + `api/discord-login.js`/`api/discord-callback.js` (login opcional com Discord, v0.8.7, ver §8.1). Só `livekit-server-sdk` é dependência npm de verdade (ver `package.json`) — os dois arquivos do Discord não precisam de nenhuma lib, só `fetch` (nativo no runtime Node do Vercel). O site em si continua sem build step nenhum.
- **Hospedagem: Vercel**. Site: `https://sinal-app-stream.vercel.app`. Deploy automático via GitHub (`git push` na `main` → produção; push em qualquer outra branch, ex: `development` → *preview deploy* com URL própria, não mexe em produção — ver §10). Antes disso o projeto passou por uma versão hospedada no Netlify (~1 dia, v0.8.0–v0.8.2) — migrado depois de bater no limite de créditos grátis de build do mês (não era um problema estrutural do Netlify, foi consumo de uma sessão de iteração rápida, ~4 deploys de produção num dia só). Os arquivos específicos do Netlify (`netlify/`, `netlify.toml`) foram removidos do projeto — ver §11 se precisar do histórico completo.
- **PWA instalável** (manifest + service worker) — dá pra "instalar" como app, sem barra de navegador, ícone próprio.

~~Por que não Electron/app nativo~~ — **desatualizado, não vale mais**. Essa frase valia num ambiente sandboxed sem acesso a ferramentas de build reais; a partir de 2026-09-22 o projeto passou a rodar com acesso de verdade a `winget`/`cargo`/MSVC/execução de processo nessa máquina, e o app desktop começou a ser construído de fato — ver §15. O site web + PWA continua existindo e sendo o jeito principal de usar o Sinal (o Electron é um segundo cliente opcional, não substitui nada).

**O que "backend" significa aqui, na prática, pros amigos**: nada muda pra quem usa — continuam só abrindo um link, sem conta, sem instalar nada. O backend é infraestrutura que só o dono do projeto configura uma vez (servidor LiveKit + variáveis de ambiente na plataforma de hospedagem).

Editar os arquivos dentro de `public/` diretamente continua sendo o fluxo normal pro site. `api/get-token.js` é o único arquivo que roda em Node (servidor).

**Por que `public/` existe (não é capricho de organização)**: o `.env` guarda a API secret do LiveKit em texto puro. Na época em que o projeto era hospedado no Netlify, a primeira versão do `netlify.toml` publicava a pasta inteira do projeto (`publish = "."`) — testei e confirmei que o Netlify CLI **não** respeita `.gitignore`/`.netlifyignore` de forma confiável pra excluir arquivos do publish. Só ficar de fora fisicamente do diretório publicado garante que o `.env` nunca vira um arquivo estático público, não importa a versão do CLI ou config de ignore. Bônus: essa mesma estrutura (`public/` na raiz) é **exatamente** a convenção zero-config do Vercel pra site estático sem framework ("Other" preset) — não precisou reestruturar nada na migração de hospedagem. **Todo arquivo novo que precisa ir pro site tem que nascer dentro de `public/`; todo arquivo sensível (segredo, config local) tem que ficar fora.**

## 5. Modelo de sala

Desde a v0.8.0, o modelo de sala é bem mais simples do que era: **não existe mais "anchor"/eleição/sucessão** — isso tudo foi a peça mais frágil e complexa do projeto quando era PeerJS puro (a v0.7.x inteira documentava um sistema de "corrida oportunista" pra decidir quem segurava o código da sala; ver §11 se precisar entender o histórico). O servidor do LiveKit **sempre está de pé** — não tem "quem segura o código", então não tem nada pra suceder.

- O código de 6 letras (`genCode()`) vira o **nome da sala** no LiveKit.
- Entrar numa sala (criando ou com um código existente) pede um token pra `api/get-token.js` (`fetch('/api/get-token?room=CODE&name=NOME&mode=create|join')`), depois conecta com `new LivekitClient.Room().connect(url, token)`.
- `get-token.js` recebe um parâmetro `mode` (`create` ou `join`, o cliente manda de acordo com qual botão foi clicado — `?mode=create|join` na query string) e trata os dois de forma diferente:
  - **`join`**: checa de verdade se a sala existe (`roomService.listRooms([room])`) antes de gerar o token. Se não existir, devolve **404** e o cliente mostra "Sala não encontrada. Confira o código." — igual sempre foi. **Corrigido em 2026-08-24** depois de um relato real: sem essa checagem, `roomJoin: true` no grant deixava o LiveKit criar uma sala vazia silenciosa pra **qualquer** código digitado (inclusive errado por engano), e a pessoa ficava sozinha achando que estava esperando o resto da galera aparecer, sem nenhum aviso do erro. Não reintroduzir essa simplificação sem pensar de novo no problema de UX que ela causava.
  - **`create`**: chama `roomService.createRoom({ name, emptyTimeout: 60, departureTimeout: 60 })` explicitamente, garantindo que a sala nasce com timeout curto (ver nota sobre `departureTimeout` logo abaixo) em vez do padrão da plataforma.
  - Se `mode` vier ausente/inesperado, o servidor trata como `join` de propósito (falha mais seguro — dá erro em vez de criar sala à toa).
- Participantes: `room.remoteParticipants` (Map identity → `RemoteParticipant`) + `room.localParticipant`. Eventos principais: `RoomEvent.ParticipantConnected`/`ParticipantDisconnected`, `RoomEvent.TrackSubscribed`/`TrackUnsubscribed` (vídeo/áudio de outros), `RoomEvent.LocalTrackUnpublished` (cobre parar de compartilhar pelo controle nativo do navegador, não só pelo nosso botão), `RoomEvent.DataReceived` (chat), `RoomEvent.ConnectionQualityChanged` (indicador de qualidade, ver §7).
- **Vídeo/áudio passa pelo servidor do LiveKit** (é um SFU, não é mais P2P direto) — cada participante manda **uma** cópia codificada pro servidor, que retransmite (sem recodificar) pra todo mundo. Isso é o que resolve o problema de CPU documentado em §11/§12: antes (malha), quem compartilhava recodificava uma vez por espectador; agora, uma vez só, não importa quantos assistem.

### 5.1 Sala morre quando fica vazia (`emptyTimeout`/`departureTimeout`)

Sem persistência de sala (igual antes): a intenção sempre foi "todo mundo sai, a sala morre". Isso **não acontecia sozinho** só com `roomJoin: true` no token — descoberto por relato real (2026-08-24): usuário e amigo saíram da sala, e o código continuou funcionando pra entrar bem depois. O comportamento padrão da plataforma pra salas criadas implicitamente (sem chamar `RoomServiceClient.createRoom()` antes) parece deixar a sala viva por bem mais tempo do que o esperado — não documentado com um número exato pelo LiveKit.

Corrigido em `get-token.js`, só no fluxo `mode=create` (ver §5): chama `roomService.createRoom({ name: room, emptyTimeout: 60, departureTimeout: 60 })` (60s = tempo de tolerância pra reload de página/reconexão rápida, sem deixar a sala "pendurada" por muito tempo). Erro nessa chamada é logado (`console.error`, aparece nos *Function Logs* do painel do Vercel) mas não interrompe o login — pior caso é a sala não ter o timeout customizado.

**Dois bugs em cadeia encontrados nisso, por um teste real (2026-08-24)**: (1) `RoomServiceClient` é uma API HTTP administrativa, precisa de `http(s)://` — a primeira versão passava `LIVEKIT_URL` (`wss://...`) direto, o que provavelmente fazia `createRoom` falhar sempre; corrigido convertendo o esquema (`wss://`→`https://`) antes de instanciar o client. (2) O erro tava sendo engolido em silêncio (`catch(e){}` vazio), então nem dava pra perceber que estava falhando — trocado por `console.error` de propósito. **Se um bug parecido acontecer nessa função de novo, checar os Function logs primeiro antes de tentar adivinhar a causa.**

**Não guardamos nada em banco de dados**, então não tem "retomar sala antiga" nem histórico — só o timeout de vida da sala em si mudou.

**⚠️ Limitação conhecida, aceita (2026-08-24)**: mesmo com `createRoom` rodando certinho (confirmado via log — `emptyTimeout`/`departureTimeout` chegam como `60` de verdade), a sala continua "existindo" pro `listRooms()` (usado pela checagem de `mode=join`, §5) bem depois desse tempo passar vazia. É um comportamento documentado do próprio LiveKit ([issue #3766](https://github.com/livekit/livekit/issues/3766), [issue #1109](https://github.com/livekit/livekit/issues/1109)), não um bug nosso — decidimos não investir mais tempo tentando contornar (impacto baixo: só significa que um código de sala bem antigo/abandonado ainda deixa entrar, sem custo extra nem risco sério pra um grupo pequeno). Ver §11 pra essa decisão.

## 6. Compartilhamento de tela e câmera

- **Tela**: `room.localParticipant.setScreenShareEnabled(true, captureOptions, publishOptions)`. `captureOptions` = `{ audio: true, resolution: {...}, surfaceSwitching: 'include' }` (`audio: true` só faz o navegador **oferecer** a opção de compartilhar áudio no seletor nativo dele — não força nada). `surfaceSwitching: 'include'` (v0.8.28, 2026-08-28) habilita o botão nativo do Chrome **"Compartilhar esta guia"**, que aparece quando a pessoa troca de aba durante o compartilhamento — dá pra trocar a fonte sem precisar parar e recomeçar. Confirmado na [doc oficial do Chrome](https://developer.chrome.com/docs/web-platform/screen-sharing-controls) que essa opção precisa ser pedida explicitamente (o padrão pode mudar/já não é garantido). `publishOptions` = `{ screenShareEncoding: {...} }` — **necessário à parte da resolução de captura**: sem isso, o LiveKit usa um bitrate automático baixo demais pra conteúdo de jogo (muito movimento/detalhe), causando pixelização visível mesmo captando em 1080p de verdade. Descoberto num teste real com amigo (2026-08-24) — a resolução de captura sozinha não garante nitidez, o `screenShareEncoding` é o que efetivamente controla o bitrate de saída.
- **Toggle de qualidade** (`#qualityBtn`, botão "HD"/"720" ao lado do de compartilhar, v0.8.4): dois presets em `SHARE_QUALITY_PRESETS` (`app.js`) — `high` (1080p/30fps, 4.5 Mbps) e `low` (720p/24fps, 2.5 Mbps, "leve"). Escolha salva em `localStorage` (`sinal:shareQuality`, pré-preenchido em `prefillShareQuality()`) e só é aplicada na **próxima vez** que `toggleShare()` iniciar um compartilhamento — não afeta uma sessão já em andamento, por isso o botão fica desabilitado (`disabled`) enquanto está compartilhando. Existe porque 4.5 Mbps sustentado de upload não é realidade pra todo mundo no grupo — dá pra quem tiver internet mais fraca escolher o preset leve sem precisar mexer em código.
- **Câmera**: `room.localParticipant.setCameraEnabled(true)` — sem áudio (nunca chamamos `setMicrophoneEnabled`), porque a voz já vai 100% pelo Discord; duplicar geraria eco.
- Convenção de id de tile: tela usa `participant.identity` puro; câmera usa `identity + ':cam'`. Isso evita colisão quando as duas estão ativas ao mesmo tempo. A diferenciação vem de `publication.source` (`Track.Source.Camera` vs `Track.Source.ScreenShare`/`ScreenShareAudio`).
- Vídeo e áudio de uma mesma fonte (ex: tela + "áudio da guia") podem chegar como tracks **separados** do LiveKit, em qualquer ordem — `handleTrackAdded`/`handleTrackRemoved` em `app.js` juntam os dois no mesmo `MediaStream` (`tileStreams`, Map tileId → MediaStream) antes de tocar no `<video>`, sem depender de qual chega primeiro.

  **Histórico da resolução (pra não reabrir esse debate à toa)**: em 2026-08-24, um amigo do usuário compartilhando Terraria viu o próprio jogo lagar, CPU consumida pelo Sinal — na época (v0.7.x, malha P2P), quem compartilha recodificava o vídeo uma vez por pessoa assistindo. Mitigação imediata: baixar pra 720p/24fps. Depois, a migração pro LiveKit (v0.8.0, §5) resolveu o problema de raiz — o multiplicador por número de espectadores não existe mais, já que o SFU só recodifica uma vez, não importa quantos assistem. Na v0.8.1, **voltado pro padrão 1080p/30fps** a pedido do usuário, já que o motivo original de baixar (escalar com espectadores) não existe mais nessa arquitetura. Resolução×framerate ainda importa pro custo de codificar **uma vez** (isso não muda com SFU nenhum) — se precisar economizar CPU de novo no futuro por algum motivo novo, esse é o objeto (`resolution` dentro de `setScreenShareEnabled` em `toggleShare()`) que se ajusta.

### 6.1 Chat de texto

Vai pelo canal de dados nativo do LiveKit: `room.localParticipant.publishData(bytes, { reliable: true, topic: 'chat' })` pra mandar, `RoomEvent.DataReceived` pra receber. Mensagem é `{type:'chat', text, ts}` (o remetente já vem separado, como o `participant` do próprio evento — não precisa embutir `id`/`name` no payload). Quem manda uma mensagem já renderiza a própria localmente (otimista) antes de mandar. Sem histórico persistido (some ao sair da sala), consistente com o resto do app.

Diferente da era PeerJS/anchor, **não existe mais risco de mensagem se perder numa troca de anchor** — o LiveKit é sempre o mesmo servidor durante toda a sessão, não tem "troca" nenhuma pra perder mensagem no meio.

**Nomes e textos vêm de outros participantes e não são confiáveis** — sempre inseridos via `escapeHtml()` (ou `textContent` direto), nunca via `innerHTML` cru. Isso vale pra qualquer lugar que mostra nome de gente (chat, tile, avatar) — não reintroduzir interpolação direta em template string dentro de `innerHTML` (era uma falha de XSS real, corrigida na v0.7.0 — ver §11). O nome de exibição (`participant.name`) é passado pro token via `AccessTokenOptions.name` (ver §8) — continua vindo de fora, continua não confiável, mesma regra vale.

⚠️ **Essa regra já falhou uma segunda vez — leia antes de confiar nela (v0.8.29, 2026-09-21).** A regra acima foi seguida à risca e mesmo assim tinha XSS armazenado. Motivo: a `escapeHtml()` original era `textContent` → `innerHTML`, que **não escapa aspas** — o serializador de HTML só escapa `&`, `<` e `>` em nó de texto. Em contexto de texto bastava; mas em `renderAvatars()`/`renderRosterPanel()` o valor ia **dentro de atributo** (`src="..."`, `data-name="..."`), e aí dava pra fechar a aspa e injetar um `onerror=`. Cadeia completa: `?avatar=` (query string, sem validação) → `metadata` do participante → LiveKit distribui pra todo mundo → `innerHTML` na tela de todos. Como o `adminProof` mora no `localStorage` e vale 30 dias, qualquer um que entrasse numa sala podia roubar poder de moderação.

Duas lições, nessa ordem de importância:

1. **Montar via DOM (`createElement` + `.textContent`/`.src`) em vez de escapar string.** É o que `renderAvatars()` e `renderRosterPanel()` fazem agora — aí a classe inteira do problema deixa de existir, em vez de depender de lembrar de escapar certo em todo lugar, toda vez. O `escapeHtml()` foi corrigido (escape manual, cobre aspas) e continua existindo pros pontos que ainda interpolam em contexto de **texto**, mas é a segunda opção, não a primeira.
2. **"Veio preenchido" nunca é prova de nada.** O `avatar` era tratado como sinal de "logou via Discord" sendo que é só um parâmetro de query. Hoje é validado no formato em `get-token.js` (só URL do CDN do Discord), o que também fecha o uso do campo como beacon de IP e como jeito de disparar o webhook sem login — mas segue sendo filtro de ruído, não autenticação (ver o comentário lá).

### 6.2 Conveniências pequenas

- **Notificação sonora**: quando alguém (que não seja você) começa a compartilhar tela/câmera, toca um "blip" curto gerado via WebAudio (`playNotifyChime()`), sem depender de arquivo de áudio externo. Como o navegador só libera som automático depois de algum gesto do usuário, o `AudioContext` é "aquecido" (`getAudioCtx()`) já no clique de "Criar sala"/"Entrar". Disparado de dentro de `addTile()` quando `!isSelf`.
- **Aviso no título da aba**: junto com o som acima, se a aba estiver em segundo plano (`document.hidden`) quando alguém começa a compartilhar, o título vira "🔴 Nova transmissão — SINAL" (`flashTabTitle()`) até você voltar a olhar pra ela. `leaveRoom()` também restaura, pra não ficar um título "preso".
- **Lembrar último código**: ao entrar numa sala (criando ou entrando), o código vai pro `localStorage` (`sinal:lastRoomCode`) e pré-preenche o campo "entrar em sala existente" na próxima visita. Link de convite (`?sala=CODE`) sempre tem prioridade sobre esse valor salvo. Chamado tanto no carregamento da página quanto ao sair de uma sala (SPA, sair não recarrega a página).
- **Lembrar último nome**: mesma lógica, pro campo "Seu nome" (`sinal:lastName`, salvo dentro de `getName()`). Só precisa pré-preencher no carregamento inicial.

### 6.3 Controles em ícone

Todos os botões de ação da tela da sala — copiar código, copiar convite, chat, câmera, compartilhar tela, sair da sala — são botões só de ícone (`.icon-btn`, 46×46px, sem texto visível), tipo barra de controle de chamada (Discord/Zoom/Meet). Rótulo acessível vira `title`/`aria-label`; pros botões que trocam de estado (câmera/compartilhar), isso é atualizado via `setBtnLabel(btn, texto)`. Feedback visual de "ligado" é só a cor (classe `.active-share`).

## 7. Grid, destaque e minimizado

- `tiles` (Map id → elemento DOM) e `pinnedOrder` (array, no máximo 2 ids) controlam o layout.
- A primeira transmissão a aparecer entra automaticamente em destaque (`.spotlight`).
- Clicar num quadro alterna fixar/desfixar (`togglePin`/`pinTile`/`unpinTile`). Máximo 2 fixados; ao fixar um terceiro, o mais antigo desce pra fileira minimizada (`.filmstrip`) automaticamente.
- Mover entre destaque e minimizado é feito com `moveTileTo`, que **reaproveita o elemento `<video>` existente** (não recria), então o stream não pausa/pisca ao trocar de posição.
- **Tamanho do tile em destaque**: `.spotlight .tile` usa `aspect-ratio:16/9; width:100%; max-height:76vh; max-width:calc(76vh * 16 / 9)` — tamanho fixo, simples, sem cálculo em JS. **Sessão de 2026-08-28 explorou (e abandonou) várias alternativas** tentando aumentar esse tile (calcular altura real via JS medindo `.room-bar`/`.controlbar`, adaptar o tile pra proporção real do vídeo compartilhado, forçar `width/height:100%` pra alinhar com as bordas da UI) — cada uma resolvia um problema e criava outro (overflow por elemento não contado, letterbox mais evidente quando o conteúdo não é 16:9, etc.), e no fim o usuário preferiu a versão original simples. **Não reabrir esse redesenho sem um motivo novo e concreto** — já foi tentado a fundo nessa sessão, com testes exaustivos, e a conclusão foi que a versão fixa é a que dá o resultado mais previsível pra qualquer formato de conteúdo compartilhado.
- Cada tile (exceto o seu próprio) tem controles no hover: mute/desmute, slider de volume (0-100, ajusta `video.volume`/`video.muted` — só afeta o que **você** ouve, local), e "desativar vídeo" (`.render-off`, dá `video.pause()` + oculta visualmente, pra economizar decodificação/CPU sem sair da chamada).
- **Indicador de qualidade** (`.quality-dot`, ao lado do nome no label do tile, só em tiles que não são seus): desde a v0.8.0, vem direto do LiveKit — `RoomEvent.ConnectionQualityChanged` já entrega `Excellent`/`Good`/`Poor` por participante (o servidor calcula isso, não precisamos mais medir `getStats()` na unha via polling como na era PeerJS). `updateQualityDot()` mapeia pros três níveis visuais (verde/âmbar/vermelho) e atualiza os dois tiles possíveis da mesma pessoa (tela e câmera) juntos, já que qualidade é por participante, não por track.
- **Detalhamento no tooltip (jitter/perda de pacote)**: além do nível Excellent/Good/Poor (que é por participante, calculado pelo servidor), o tooltip (`title` do `.quality-dot`) agora também mostra números por track, amostrados no cliente a cada 4s via `track.getRTCStatsReport()` (API pública do LiveKit Client SDK, `RemoteTrack`/`LocalTrack`) — `sampleTileDetailedStats()` procura a entrada `inbound-rtp`/`kind:'video'` no `RTCStatsReport`, calcula **perda em delta** (`packetsLost`/`packetsReceived` são cumulativos desde o início da conexão, então guardamos o valor anterior em `qualityStatsPrev` e comparamos a diferença — perda "instantânea" recente, não a média da chamada toda) e converte `jitter` de segundos pra ms. `qualityBaseLabel` (texto vindo do evento nativo) e `qualityDetails` (texto amostrado) são combinados por `renderQualityTooltip()`, resultado tipo `"Boa conexão · perda: 0.5% · jitter: 12ms"`. `tileVideoTracks` (Map tileId → track) alimenta o loop de amostragem e é populado/limpo junto com `handleTrackAdded`/`handleTrackRemoved`/`leaveRoom`.
- **Cuidado (não repetir)**: uma tentativa anterior de aumentar só a área de hover do `.quality-dot` (via `padding` + `background-clip:content-box`, mantendo o círculo visual pequeno) quebrou porque `.quality-dot.good/.warn/.bad` usa a propriedade abreviada `background` — isso reseta `background-clip` de volta pro padrão (`border-box`) nessas classes, e a bolinha colorida pintava a área de hover inteira (ficava visivelmente maior). Revertido; se reaplicar essa ideia no futuro, as classes `.good/.warn/.bad` precisam usar `background-color` (não `background`) pra não resetar o clip.
- **Painel "quem está na sala"** (`#rosterBtn`/`#rosterPanel`, botão de pessoas ao lado do chat na `room-bar`): abre uma barra lateral (mesmo padrão visual/estrutural do `.chat-panel` — `position:fixed`, desliza da direita, `translateX`) listando cada participante com avatar (iniciais) + nome + "(você)" + tag "Compartilhando" quando aplicável; avatar ganha borda vermelha (`.roster-row.sharing .roster-avatar`) igual ao destaque que já existia nos avatares do topo. `toggleRosterPanel()`/`renderRosterPanel()` em `app.js`. **Chat e roster se fecham mutuamente** (abrir um fecha o outro — ambos ocupam o mesmo canto da tela) e ambos fecham ao sair da sala.

## 8. Backend: função serverless + LiveKit self-hosted

- **`api/get-token.js`** (função do Vercel, disponível em `/api/get-token`): recebe `room`, `name` e `mode` (`create`/`join`) via query string. Se `mode=join`, checa via `roomService.listRooms([room])` se a sala existe de verdade antes de gerar token (senão devolve 404 — ver §5). Se `mode=create`, chama `roomService.createRoom({ name, emptyTimeout: 60, departureTimeout: 60 })` pra garantir timeout curto (ver §5.1). Depois monta um `AccessToken` (SDK oficial `livekit-server-sdk`) com `identity` gerada (nome + sufixo aleatório, pra permitir nomes repetidos/reconexão em outra aba sem colidir), `name` = nome de exibição, grants `{ roomJoin: true, room, canPublish: true, canSubscribe: true, canPublishData: true }`, devolve `{ token, url }` em JSON. **Lê `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET`/`LIVEKIT_URL` de variáveis de ambiente** — a API secret nunca aparece no navegador, é exatamente o motivo dessa função existir (ver comentário no topo do arquivo).
- `RoomServiceClient` (API HTTP administrativa) precisa de `http(s)://`, diferente do `wss://` que o cliente usa — a função converte o esquema da `LIVEKIT_URL` antes de instanciar. Erros de `createRoom`/`listRooms` são logados (`console.error`, aparecem nos logs de função da plataforma) em vez de engolidos em silêncio — já causou um bug real escondido antes disso (ver §11).
- TTL do token: sem valor customizado, usa o padrão do SDK (6h) — de propósito, pra não cair no meio de uma sessão longa de call/jogo.
- **STUN/TURN**: até 2026-08-27, o LiveKit Cloud cuidava disso internamente. Desde a migração pro self-host (v0.8.19, ver §12), o **próprio servidor da Oracle roda o TURN** (via o campo `turn:` do `livekit.yaml`, gerado pelo assistente oficial `livekit/generate`) — não precisou reintroduzir nenhuma config manual de ICE server no cliente, o LiveKit Client SDK descobre isso sozinho a partir da URL do servidor. Toda a config antiga da era PeerJS (`STATIC_ICE_SERVERS`, busca de TURN dinâmico em `elixir-webrtc.org`, o botão de "testar minha conexão") continua removida desde a v0.8.0 e não precisou voltar.

### 8.1. Login opcional com Discord (v0.8.7)

- **Por quê**: o grupo já vive no Discord (voz fica lá, só a tela é compartilhada pelo Sinal) — dá pra puxar nome + avatar reais em vez de digitar nome à mão toda vez. **Explicitamente opcional** (pedido do usuário) — o fluxo de sempre (campo de nome livre) continua existindo do lado, sem nenhuma obrigatoriedade.
- **Sem sessão no servidor**: o Sinal continua sem banco de dados/estado. O OAuth só é usado uma vez pra perguntar ao Discord "quem é essa pessoa" (nome + avatar); a resposta fica salva no `localStorage` do navegador (`sinal:discordUser`), igual `sinal:lastName` já funcionava. Não tem refresh token, não revalida com o Discord depois — é só uma foto do perfil no momento do login. É por isso que "fica salvo" sem precisar refazer o login toda visita (até a pessoa clicar em "trocar" ou limpar os dados do site).
- **Fluxo (OAuth2 Authorization Code padrão)**:
  1. Botão "Entrar com Discord" na tela inicial (`loginWithDiscord()` em `app.js`) manda o navegador pra `/api/discord-login`, levando o código de sala já digitado (se tinha algum) como query `?sala=`.
  2. **`api/discord-login.js`**: monta a URL de autorização do Discord (`client_id` do env `DISCORD_CLIENT_ID`, `redirect_uri` **derivado da própria origem da requisição** — `new URL(request.url).origin + '/api/discord-callback'`, igual o truque de conversão de esquema da `LIVEKIT_URL` — não fixo em código) e redireciona. O `sala` (se veio) vira o `state` do OAuth, só pra sobreviver o vai-e-volta. A pessoa loga **no site do Discord**, a senha nunca passa pelo Sinal.
  3. **`api/discord-callback.js`**: troca o `code` pelo `access_token` (`POST discord.com/api/oauth2/token`, usando `DISCORD_CLIENT_SECRET` — só aqui, nunca no navegador, mesma cautela da `LIVEKIT_API_SECRET`), busca o perfil (`GET discord.com/api/users/@me`), monta a URL do avatar (`cdn.discordapp.com/avatars/{id}/{avatar}.png`, com fallback pro avatar padrão do Discord via fórmula `(id >> 22) % 6` quando a pessoa não tem avatar customizado — precisa de `BigInt` porque o ID do Discord estoura a precisão segura de `Number`), e redireciona de volta pra `/` com `?discord_name=...&discord_avatar=...` (+ `sala=...` se tinha).
  4. `app.js`: `handleDiscordCallback()` roda no `DOMContentLoaded` (antes de `prefillLastName()`), detecta esses parâmetros, salva em `sinal:discordUser`, e limpa a URL (`history.replaceState`) sem perder o `?sala=`.
- **Sem assinatura/criptografia no round-trip** — de propósito, não por descuido: o nome/avatar que voltam do callback só controlam o que a **própria pessoa** vê como identidade dela no Sinal, exatamente como o campo de nome livre já funcionava antes. Não é um token de acesso a nada — ninguém ganha permissão de mais nada só "forjando" esses parâmetros.
- **Avatar de verdade pros OUTROS participantes, não só localmente**: `connectToRoom()` manda o avatar salvo junto com `room`/`name`/`mode` pra `/api/get-token`, que grava isso no campo `metadata` do `AccessToken` do LiveKit (`{ avatarUrl }` em JSON) — assim todo mundo na sala recebe o avatar via `participant.metadata`, não só quem logou. `renderAvatars()` (avatares do topo) e `renderRosterPanel()` (barra lateral) checam `participantAvatarUrl(p)` e trocam as iniciais por `<img>` quando tem avatar; sem Discord, cai nas iniciais de sempre — nada quebra pra quem não usa.
- **Checklist de setup** (contas/infra do usuário, não dá pra eu fazer por ele):
  1. Criar uma aplicação em https://discord.com/developers/applications, pegar **Client ID** e gerar um **Client Secret**.
  2. Na aba OAuth2 dessa aplicação, registrar os **Redirects** exatos (Discord exige correspondência exata, não aceita coringa): `https://sinal-app-stream.vercel.app/api/discord-callback` (produção) e o domínio do preview da `development` (ex: `https://sinal-app-git-development-<algo>.vercel.app/api/discord-callback`) — e opcionalmente `http://localhost:3000/api/discord-callback` pra testar com `vercel dev` (Discord permite `http://localhost` como exceção pra desenvolvimento local).
  3. Configurar `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET` no `.env` local e no painel do Vercel (Environment Variables), mesmo padrão das 3 variáveis do LiveKit.
  4. ✅ **Testado ponta a ponta com sucesso** (2026-08-24): app Discord criada, chaves configuradas, login/autorização/avatar real funcionando pro próprio usuário e pros outros participantes na sala.

### 8.2. Moderação (admin fixo via Discord)

Pedido explícito do usuário (2026-08-24), quebrando conscientemente o princípio de "sem anfitrião, todo mundo com os mesmos privilégios" (§1) — decisão dele, documentada aqui pra não ser desfeita sem motivo.

- **Quem é admin**: não é "quem criou a sala" (seria por sala, temporário) — é um **Discord ID fixo**, configurado em `ADMIN_DISCORD_IDS` (env var, lista separada por vírgula), sempre admin em qualquer sala que entrar. Só funciona pra quem logou com Discord (§8.1).
- **Ações disponíveis**: expulsar da sala (botão na barra lateral "quem está na sala", só aparece pro admin, com `confirm()` antes), desligar a tela ou a câmera de alguém remotamente (menu `⋮` que aparece ao passar o mouse no tile de vídeo dela).
- **Como confirma "essa pessoa é o Discord ID X" sem sessão/banco de dados** — dois hops de assinatura, cada um verificável sem estado:
  1. `api/discord-callback.js`, depois de confirmar via OAuth real, checa `ADMIN_DISCORD_IDS`; se bater, assina um comprovante pequeno (`{id, exp}` + HMAC-SHA256, `lib/adminProof.js`) usando `DISCORD_CLIENT_SECRET` como chave (reaproveitado de propósito, pra não precisar de mais uma env var — decisão pragmática pro contexto de grupo pequeno de amigos, não reabrir sem motivo real). Validade: 30 dias, guardado em `sinal:discordUser.adminProof` no `localStorage` — "fica salvo" igual nome/avatar.
  2. `api/get-token.js` verifica esse comprovante (`verifyAdminProof`); se válido, adiciona `roomAdmin: true` ao grant do `AccessToken` do LiveKit — campo **nativo** do `livekit-server-sdk` (`node_modules/livekit-server-sdk/dist/grants.d.ts`), feito exatamente pra isso.
  3. `api/moderate.js` (novo endpoint) recebe o **mesmo token do LiveKit** que o navegador já usa em `room.connect()` (via header `Authorization: Bearer`), verifica com `TokenVerifier` (também do SDK) e confere `claims.video.roomAdmin === true` + `claims.video.room === room` antes de chamar `roomService.removeParticipant()` ou `roomService.mutePublishedTrack(..., true)`.
- **Reação de quem foi mutado à força**: `RoomEvent.TrackMuted` em `app.js` detecta quando é a própria track (Camera/ScreenShare) sendo mutada e chama `setScreenShareEnabled(false)`/`setCameraEnabled(false)` de verdade (não deixa só "mutado mas ainda capturando") — isso já dispara o `LocalTrackUnpublished` existente, que reseta os botões sozinho.
- **Limitação honesta, aceita de propósito**: isso é moderação **social**, não uma trava técnica inquebrável — quem foi mutado pode simplesmente clicar em compartilhar de novo na hora (o LiveKit não impede republicar). Pra um grupo pequeno de amigos, o objetivo é dar um sinal claro ("o admin desligou isso"), não impedir fisicamente. Expulsar é mais definitivo, mas nada impede reentrar se a pessoa ainda tiver o código da sala.
- **Configuração pendente do usuário**: falta criar/definir `ADMIN_DISCORD_IDS` no `.env` local e no painel do Vercel (todos os ambientes) com o Discord ID numérico dele.

#### Bugs achados no primeiro teste real (2026-08-24)

- ✅ **Expulsar não devolvia a pessoa expulsa pra tela inicial** — `RoomEvent.Disconnected` só mostrava uma mensagem de erro e deixava a pessoa presa na tela da sala, sem conseguir fazer nada (ela via os próprios controles, mas a conexão já tinha caído). **Fix (confirmado funcionando)**: o handler agora chama `leaveRoom()` de verdade (reseta tudo e volta pra tela de entrada) e mostra "Você foi desconectado da sala." — cobre expulsão e qualquer outra desconexão inesperada (queda de rede etc), não só expulsão.
- ✅/❌→✅ **`RoomEvent.TrackMuted` reagindo pra desligar tela/câmera à força quebrou o toggle normal de qualquer usuário — revertido, não reintroduzir sem entender o timing real do evento**. Tentativa 1 (v0.8.9): reagir a `TrackMuted` chamando `setCameraEnabled(false)`/`setScreenShareEnabled(false)` de volta quando o admin muta alguém à força. Descoberto em teste real que `TrackMuted` **também** dispara como efeito colateral do próprio `toggleShare()`/`toggleCamera()` desligando normalmente — a reação reentrava em cima da chamada original. Tentativa 2 (mesmo v0.8.9, minutos depois): guardar com uma flag (`selfInitiatedDisable`) setada durante a chamada própria. **Mock local confirmou que a flag suprimia a reentrância corretamente** — mas o usuário testou de novo contra o LiveKit real e o problema **continuou idêntico**, tanto no toggle próprio quanto no mute do admin (câmera "presa" ligada pros outros, botão de religar inútil). Ou seja: **o timing real do `TrackMuted` no LiveKit não bate com o que o mock simulava** — o evento provavelmente dispara fora da janela que a flag cobre (ex: só depois de um round-trip de confirmação do servidor, não sincronicamente dentro do `await` local). **Decisão final: removida a reação a `TrackMuted` por completo** (v0.8.9, segunda correção) — `toggleShare()`/`toggleCamera()` voltaram exatamente ao formato original de antes dessa sessão (sem flag, sem guard). Efeito colateral aceito: quem é mutado à força pelo admin não tem o próprio botão resetado automaticamente (precisa clicar ela mesma pra perceber/corrigir) — mas o toggle normal (ligar/desligar a própria câmera) volta a funcionar sem regressão. **Lição pra não repetir**: mock local não é confiável pra validar timing de eventos do LiveKit real — qualquer reação automática a eventos de mute precisa ser testada contra o servidor de verdade antes de considerar resolvida, não só localmente.
- ✅ **Causa raiz de verdade encontrada (v0.8.12), via log real** (não mock): `setCameraEnabled(false)`/`setScreenShareEnabled(false)` **não desligam a track — só MUTAM** (a publicação continua existindo, com o mesmo `trackSid`, só `isMuted: true`). Log real confirmando: `pub antes: {muted:false, trackSid:'TR_...'}` → `pub depois: {muted:true, trackSid:'TR_...'}` (mesmo trackSid, publicação nunca some). Isso explica os dois bugs de uma vez: (1) `toggleCamera()`/`toggleShare()` checavam só `if(pub)` pra decidir liga/desliga — uma publicação mutada ainda é "verdadeira", então todo clique seguinte repetia a chamada de desligar (já mutado, sem efeito) em vez de religar; (2) como a publicação nunca era removida de verdade, `TrackUnsubscribed` nunca disparava pros outros participantes, e o tile ficava congelado pra sempre (tanto no toggle próprio quanto no mute forçado por admin). **Fix de verdade**: trocado `setCameraEnabled(false)`/`setScreenShareEnabled(false)` por `room.localParticipant.unpublishTrack(pub.videoTrack)` (e também o `ScreenShareAudio` se tinha áudio compartilhado) — isso remove a publicação de fato, dispara `LocalTrackUnpublished`/`TrackUnsubscribed` corretamente, e o próximo clique corretamente cai no "ligar" de novo. Testado com mock que modela o comportamento REAL confirmado por log (mute-only em `setCameraEnabled`, remove de verdade em `unpublishTrack`) — 4 ciclos seguidos de liga/desliga/liga/desliga confirmados funcionando.
- ✅ **Tile congelado pros outros quando alguém é mutado remotamente (admin)** — como a track mutada continua publicada (mesmo raciocínio acima), o tile de quem foi mutado pelo admin ficava congelado indefinidamente pros outros, sem nenhum sinal visual. **Fix**: `RoomEvent.TrackMuted`/`TrackUnmuted` pra participantes **remotos** (não o próprio usuário) agora aplicam/removem a classe `render-off` no tile automaticamente (reaproveitando o mesmo mecanismo visual do botão manual "desativar vídeo" que cada um já tinha) — testado com mock, confirmado indo `render-off` → sem a classe corretamente.
- ✅ **Logs de diagnóstico removidos** (2026-08-28) — os `console.log('[sinal] ...')` em `moderateAction`/`api/get-token.js`/`api/moderate.js` foram tirados depois de confirmar a moderação estável por um tempo (kick/mute testados e funcionando várias vezes, inclusive uso real). Os `console.error` de erro genuíno continuam, só o log de sucesso "de propósito" foi removido.
- ✅/🔄 **3ª tentativa: desligar de verdade quem foi mutado por um admin (v0.8.13)** — pedido explícito do usuário depois de entender a limitação (ver acima): `mutePublishedTrack` só para o LiveKit de retransmitir, não desliga a captura de quem foi mutado — se a pessoa sair do PC com câmera/tela ligada e mais ninguém estiver vendo, continua consumindo banda à toa. Motivo concreto: já preocupados com o teto de 50GB/mês do plano free (ver §10), o admin precisa poder **interromper de verdade**, não só esconder visualmente. Reintroduzido o handler de `TrackMuted` reagindo pro próprio usuário — mas dessa vez chamando `unpublishTrack()` (o método correto, já confirmado funcionando no toggle próprio) em vez de `setCameraEnabled(false)` (que só muta, era a causa dos dois bugs anteriores). Guard `selfInitiatedUnpublish` (mesmo padrão de antes, agora aplicado ao método certo) evita reagir ao próprio `unpublishTrack()` do toggle normal, caso ele também emita `TrackMuted` como parte do processo. **Testado com mock reproduzindo exatamente esse cenário** (TrackMuted disparando no meio do próprio unpublishTrack) — sem reentrância, ciclos de liga/desliga seguem funcionando, e mute genuíno de admin (fora do guard) dispara o unpublish corretamente. **✅ Testado e confirmado contra o LiveKit real (2026-08-25)** — expulsar, desligar tela e desligar câmera funcionando de ponta a ponta, inclusive validado num caso de uso real (usuário removeu um amigo de verdade da call).
- ✅ **Coroa (👑) indicando quem é o admin** (v0.8.14) — pedido do usuário depois de validar a moderação. `api/get-token.js` agora inclui `isAdmin` no `metadata` do participante (junto do `avatarUrl` já existente, ver §8.1) quando o `adminProof` é válido — assim TODOS os participantes enxergam quem é admin, não só quem logou. `participantIsAdmin(p)` em `app.js` lê isso e mostra a coroa em três lugares: label do tile de vídeo, linha do participante no painel "quem está na sala", e tooltip do avatar no topo. Testado com mock, aparece só pra quem tem `isAdmin:true` no metadata.
- **Formato Vercel**: `export async function GET(request) { ... return new Response(...); }` — Web Handler padrão (`Request` in, `Response` out), export nomeado pelo verbo HTTP. Cada arquivo em `api/` vira uma rota (`api/get-token.js` → `/api/get-token`).

## 9. PWA e versionamento

- `manifest.json`: `start_url: "./"` (não usar `"./index.html"` — isso gerava link de convite feio com `/index.html` no final; já foi corrigido uma vez, não reintroduzir).
- `sw.js`: estratégia **network-first** (tenta buscar da rede sempre; só cai pro cache se estiver offline). `SHELL` agora inclui `style.css` e `app.js` além de `index.html`/`manifest.json`/ícones — se adicionar mais arquivos estáticos no futuro, lembrar de incluir aqui também.
- **Versionamento**: `APP_VERSION` (dentro de `app.js`) e `CACHE` (dentro do `sw.js`) precisam ser incrementados **juntos**, a cada mudança publicada. É assim que o navegador percebe que existe versão nova e mostra a barra "Nova versão disponível". **Se esquecer de mudar o `CACHE`, o mecanismo de atualização simplesmente não dispara.**
- Convenção acordada com o usuário: semver simples `0.1.0`, `0.2.0`, `0.3.0`... — sobe a **minor** a cada leva de mudanças relevantes publicada, `1.0.0` fica reservado pra quando o usuário considerar o projeto "redondo".
- `0.7.0` foi publicada (2026-08-24) — última versão da era PeerJS/malha.
- `0.8.0` publicada (2026-08-24) — migração completa pro LiveKit Cloud (SFU) + separação HTML/CSS/JS + estrutura `public/`. Deploy via `netlify deploy --prod`, testado com 2 participantes reais antes de publicar (§12).

- **Créditos gratuitos do Netlify Drop expiram em 1h se não reivindicados** — o usuário já reivindicou o site atual (irrelevante agora que o Netlify é legado, mas documentado por histórico).
- **Migração de hospedagem Netlify → Vercel, 2026-08-24**: motivada por limite de créditos de build do Netlify batido no meio de uma sessão de deploy rápido (não um problema estrutural do Netlify em si — ver §10 pro racional completo). Trocou também o método de deploy: de comando manual (`netlify deploy --prod`) pra automático via GitHub (`git push`). Netlify não foi desativado, só parou de receber deploy novo. **Não reabrir "qual provedor usar" sem motivo novo real** — já foi decidido, com o usuário citando experiência prévia concreta com o Vercel aguentando ritmo de deploy parecido sem problema.
- **Migração de malha P2P (PeerJS) pra SFU gerenciado (LiveKit Cloud), v0.8.0 (2026-08-24)**: motivada por um relato real — amigo compartilhando Terraria via CPU disparar, porque na malha quem compartilha recodifica uma vez por espectador. Eliminou de vez toda a máquina de "anchor"/eleição/sucessão (era a peça mais frágil do projeto — ver histórico da v0.5.0/v0.7.x se precisar entender o que existia antes) e a config de STUN/TURN próprio (agora é responsabilidade do LiveKit Cloud). Usuário escolheu explicitamente: SFU **gerenciado** (não auto-hospedado) e SDK **oficial** do LiveKit pra gerar token (não montado na mão) — ver plano de implementação salvo em `lazy-drifting-falcon.md` (histórico da conversa) se precisar do racional completo. **Não reintroduzir PeerJS nem a lógica de anchor** a menos que o usuário peça explicitamente pra voltar atrás.
- **Separação em `index.html`/`style.css`/`app.js`, v0.8.0**: o usuário achava o arquivo único confuso — pedido dele, feito junto com a migração pro LiveKit já que era uma reescrita grande de qualquer jeito. Continua sem bundler/build step pro site.
- **"Desconectado da sala" aparecendo por cima de uma conexão nova que funcionava** (relato real, 2026-08-24, testado em produção): `room.disconnect()` (chamado em `leaveRoom()`) é assíncrono — sair e reentrar rápido (mesmo código ou outro) podia deixar a sala **nova** já conectada e funcionando enquanto o evento `RoomEvent.Disconnected` da sala **antiga** ainda estava a caminho. Como os handlers escrevem em elementos de UI compartilhados (`#roomStatus`), o eco atrasado da sala velha aparecia por cima do estado real da sala nova. Corrigido em `wireRoomEvents()`: todo handler registrado ali só age se a instância de `Room` que ele pertence (`liveRoom`, capturada no closure) ainda for a sala atual (comparação `liveRoom === room`, a variável global) — evento de uma instância abandonada é ignorado. **Esse padrão (`isCurrent()`) precisa continuar em qualquer handler novo que for adicionado em `wireRoomEvents()`** — não voltar a registrar handler sem essa checagem.
- **Arquivos do site movidos pra dentro de `public/`, v0.8.0**: a primeira versão do `netlify.toml` tinha `publish = "."` (raiz inteira), o que deixaria o `.env` (API secret do LiveKit em texto puro) exposto como arquivo estático público — descoberto e corrigido antes de qualquer deploy, depois de pesquisar e achar relatos de que o Netlify CLI não respeita `.gitignore`/`.netlifyignore` de forma confiável pra excluir arquivos do publish. Solução adotada: exclusão **estrutural**, não por config de ignore — só `public/` é publicado, `.env`/`netlify.toml`/`package.json`/`netlify/` ficam fora por definição. **Não voltar pra `publish = "."` com o `.env` na raiz do projeto** — se precisar reorganizar de novo, manter esse princípio (segredo sempre fora da árvore publicada, garantido pela estrutura de pastas, não por uma lista de exclusão).
- Os bugs específicos de PeerJS/anchor documentados em versões anteriores deste arquivo (eleição em cascata, anchor se autodestruindo, avatar duplicado, timeout de sala vazia) **não se aplicam mais** — essa arquitetura inteira foi removida na v0.8.0. Não é preciso reaplicar essas correções numa reescrita futura pra PeerJS a menos que o projeto volte atrás conscientemente.

Oficialmente é só uma pré-autorização temporária que o banco libera sozinho em 3-5 dias, mas a Oracle tem histórico pior que o normal nesse processo indo bem.
    - Complexidade técnica adicional (fora do escopo financeiro): precisa abrir faixa grande de portas UDP (~10 mil portas) no firewall, arquitetura ARM (imagens Docker precisam suportar arm64), e o self-host tira a garantia de "sempre online" que o Cloud gerenciado dá (agora depende da VM ficar de pé, não mais do PC do usuário — isso melhora em relação a self-host na própria máquina, mas ainda é responsabilidade nova).
    - **Decisão final (2026-08-26): seguir com a migração pra self-host na Oracle Cloud.** Riscos residuais (cartão, ociosidade) considerados aceitáveis pelo usuário. Pesquisa adicional confirmou: banda de pico da VM A1.Flex é **1 Gbps por OCPU (2 Gbps total com 2 OCPUs)** — não os 50 Mbps que apareceram numa busca inicial (esse número era da shape AMD Micro, não da ARM A1; corrigido antes de virar decisão). Portas de firewall exigidas pelo deploy oficial do LiveKit (`docs.livekit.io/transport/self-hosting/vm/`): `443/tcp`, `80/tcp`, `7881/tcp`, `3478/udp`, `50000-60000/udp`. Precisa de um domínio/subdomínio (Let's Encrypt não emite certificado pra IP puro) — usar um subdomínio grátis (ex: DuckDNS), não comprar domínio de verdade. IP público: default é efêmero, mas dá pra reservar um fixo de graça (até 2 inclusos no Always Free). **Achado importante**: o código do Sinal (`api/get-token.js`, `api/moderate.js`, `lib/adminProof.js`, `app.js`) é 100% agnóstico a LiveKit Cloud vs self-host — só depende de 3 env vars (`LIVEKIT_URL`/`API_KEY`/`API_SECRET`), confirmado sem nenhuma referência hardcoded a `livekit.cloud` no código. Migração é essencialmente trabalho de infraestrutura, não de programação. Plano completo de execução salvo localmente no momento da decisão — consultar se uma sessão futura precisar retomar de onde parou.
    - **v0.8.16: modo manutenção ativado como primeiro passo** — `MAINTENANCE_MODE = true` no topo de `app.js`, bloqueia a tela de entrada e mostra `#maintenanceScreen` (novo, em `index.html`) enquanto a migração acontece. Reversível trocando só essa flag pra `false` — usado de ida e volta 3 vezes durante a migração (ver §9, v0.8.16-0.8.19) conforme o LiveKit Cloud ainda funcionava ou não.

### Migração pro self-host — execução completa (2026-08-27 a 2026-08-28)

O limite do LiveKit Cloud **estourou de verdade** em 2026-08-27 (confirmado no painel de Billing: 5.000/5.000 min de participante usados, conexões novas falhando na hora — exatamente como a documentação oficial previa, ver acima). A partir daí a migração pro self-host (planejada em §12 acima) foi executada de ponta a ponta:

- **Conta Oracle criada, cartão cadastrado**: hold de verificação de R$5,24, **estornado automaticamente na hora** (não levou os 3-5 dias documentados, nem gerou a fricção que os relatos de fórum descreviam) — risco aceito na decisão anterior não se concretizou.
- **`VM.Standard.A1.Flex` (a shape ARM mais forte, 2 OCPU/12GB) nunca conseguiu ser provisionada** — erro `500-InternalError, Out of host capacity` em **18 tentativas seguidas**, espalhadas por um dia inteiro (madrugada, manhã, tarde, noite), tanto manualmente quanto via stack salvo no Resource Manager (`sinal-vm-stack`, criado especificamente pra facilitar retry sem repreencher o assistente). - **Decisão: testar a segunda shape Always Free, `VM.Standard.E2.1.Micro`** (AMD, 1/8 de OCPU, 1GB RAM) — historicamente bem menos disputada, provisionou **na hora**, sem fila. Duas correções de pesquisa feitas nesse processo (confirmadas direto no HTML bruto da doc oficial da Oracle, não só resumo de IA, depois de uma primeira checagem ter dado um número errado): banda real dessa shape é **480 Mbps** (não 50 Mbps como uma pesquisa anterior tinha apontado — número trocado com o de outra shape); o gargalo real dela é CPU/RAM (fração de núcleo, 1GB), não rede. Confirmado também na doc oficial (`config-sample.yaml` do LiveKit no GitHub) que **Redis é opcional** — só necessário pra deploy distribuído/multi-nó, dispensável numa VM só — mas o assistente `livekit/generate` só oferece "usar Redis externo" ou "empacotar um Redis" (não "nenhum"), então aceitamos o Redis empacotado mesmo (é leve, ~10MB de RAM, não valia brigar por isso).
- **DNS**: subdomínio grátis via [DuckDNS](https://www.duckdns.org) (conta via GitHub, sem senha nova) — dois registros, `sinal-app.duckdns.org` (principal) e `sinal-turn.duckdns.org` (TURN), ambos apontando pro IP público da VM. **Atualizado em 2026-08-28**: reservado um IP fixo (valor no painel da Oracle, grátis, até 2 inclusos no Always Free) pra substituir o efêmero original — processo: criar o IP reservado em Networking → IP Management → Reserved Public IPs, depois na VNIC da instância (IP administration → editar o IP privado) trocar "Ephemeral" por "Reserved public IP", selecionando o já criado. Os registros do DuckDNS foram atualizados pro IP novo — como o app usa o domínio (não o IP direto), não precisou tocar em `.env`/Vercel. **Pegadinha encontrada na hora**: depois de trocar o IP, criar sala parou de funcionar (dava timeout de 10s de verdade, não instantâneo como o caso do Brave Shields) — o LiveKit detecta e guarda o próprio IP público **na hora que o container sobe**, e continuou anunciando o IP antigo nos candidatos de conexão WebRTC mesmo depois da Oracle já rotear pro novo. **Fix**: `sudo systemctl restart livekit-docker` na VM — reinicia os 3 containers, o LiveKit re-detecta o IP atual do zero. **Sempre que o IP público da VM mudar por qualquer motivo, reiniciar esse serviço depois** — não é automático.
- **Firewall — duas camadas, não uma** (pegadinha já prevista no plano, confirmada na prática): (1) o Security List da VCN na Oracle (nível de nuvem) precisa liberar `443/tcp+udp`, `80/tcp`, `7881/tcp`, `3478/udp`, `50000-60000/udp`; **e também** (2) a própria VM tem um `iptables` interno pré-configurado pelas imagens Ubuntu da Oracle que só libera a porta 22 e rejeita todo o resto por padrão — passar só pelo Security List não é suficiente. Corrigido com `iptables -I INPUT 5 -p <tcp|udp> --dport <porta> -j ACCEPT` (inserido antes da regra final de REJECT) pra cada porta, persistido com `iptables-persistent`/`netfilter-persistent save` (pacote já vinha instalado na imagem).
- **Deploy**: assistente oficial `livekit/generate` rodado **direto na VM via SSH** (não localmente — o usuário não tinha Docker Desktop instalado, e instalar Docker só na VM, que já precisava dele mesmo, saiu mais simples que instalar Docker Desktop no Windows). Escolhas no assistente: "LiveKit Server only" (sem Egress/Ingress, não usamos), Let's Encrypt, versão `latest`, Redis empacotado (ver acima), "Startup Shell Script" (não cloud-init, já que a VM já existia). O `init_script.sh` gerado escreve tudo em `/opt/livekit`, registra um serviço `systemd` (`livekit-docker`, sobe sozinho se a VM reiniciar) com 3 containers: `livekit-server`, `redis` e `livekit/caddyl4` (faz o roteamento de TLS por SNI entre os dois domínios num único `:443`, usando `layer4` do Caddy).
- **Confirmado funcionando de ponta a ponta**: certificados TLS emitidos automaticamente via Let's Encrypt pros dois domínios já no primeiro boot; `curl https://sinal-app.duckdns.org/` devolve `OK`. **Consumo de recursos ocioso**: só **11.5MB de RAM no total dos 3 containers**, com **481MB ainda disponíveis** de 954MB totais na VM — bem mais folga do que o medo inicial sobre essa máquina fraca (ver §12 acima). Ainda não confirmado o comportamento sob uso real sustentado com vários compartilhamentos simultâneos por muito tempo — ver "Acompanhando o consumo" logo abaixo.

## 14. Content-Security-Policy (ligada na v0.8.30) — leia antes de adicionar recurso externo

A CSP mora no `vercel.json`, no bloco `headers`, aplicada a `/(.*)`. Ela é **defesa em profundidade**: mesmo com o XSS da §6.1 corrigido, se um dia escapar outro, a CSP transforma "script executa" em "tentativa bloqueada".

O valor atual, e o porquê de cada parte:

| Diretiva | Valor | Motivo |
|---|---|---|
| `script-src` | `'self' https://cdn.jsdelivr.net` | `app.js` e o analytics da Vercel (`/_vercel/...`, mesma origem) + o `livekit-client` do CDN. **Sem `'unsafe-inline'` de propósito** — é o que dá valor real à CSP. |
| `style-src` | `'self' https://fonts.googleapis.com` | `style.css` + a folha do Google Fonts. Também sem `'unsafe-inline'`. |
| `font-src` | `'self' https://fonts.gstatic.com` | os arquivos de fonte que a folha do Google puxa (domínio **diferente** do `style-src`, pegadinha comum). |
| `img-src` | `'self' data: https://cdn.discordapp.com` | ícones do app + avatares do Discord. |
| `connect-src` | `'self' https: wss:` | **propositalmente largo**: a URL do LiveKit vem da env var `LIVEKIT_URL` e já mudou uma vez (Cloud → self-host). Fixar o domínio aqui faria a CSP quebrar o app em silêncio no dia que o servidor mudasse de endereço. Trade-off aceito: `connect-src` serve contra exfiltração, que é secundário perto do `script-src`. |
| `frame-ancestors` | `'none'` | clickjacking em cima dos botões de moderação. Acompanhado de `X-Frame-Options: DENY` pra navegador antigo. |
| `object-src` / `base-uri` / `form-action` | `'none'` / `'self'` / `'self'` | endurecimento barato, nada no app usa. |

⚠️ **Duas regras que a CSP impõe pra sempre daqui pra frente:**

1. **Nada de `onclick="..."` (nem `onchange`, `onsubmit`, etc.) no HTML.** Todo botão é ligado por `addEventListener` no bloco no fim do `app.js` — botão novo entra naquela lista. Com CSP, handler inline não dá erro na tela: o botão só não faz nada, o que é bem pior de diagnosticar.
2. **Nada de `style="..."` inline no HTML.** Use classe no `style.css` (foi o que a tela de manutenção virou: `.on`). Mexer em `elemento.style.prop` pelo JS **continua funcionando normalmente** — a CSP não bloqueia CSSOM, só o atributo no markup.

**Recurso externo novo (CDN, fonte, API, domínio) exige adicionar o domínio na diretiva certa**, senão o navegador bloqueia e o sintoma costuma ser silencioso.

**Como testar antes de publicar**: a CSP não aparece rodando o `public/` num servidor estático qualquer — os headers vêm do `vercel.json`, que só é aplicado pela Vercel. Na sessão da v0.8.30 isso foi contornado com um servidor de teste que **lê o `vercel.json` real** e reemite os mesmos headers (`csp-test` no `.claude/launch.json`), pra não testar uma coisa e publicar outra. Vale refazer esse caminho em qualquer mudança de CSP: subir, abrir o console do navegador e procurar por `Refused to...` — é assim que violação aparece.

## 15. App desktop (Electron) — em andamento, começado em 2026-09-22

**Motivação**: navegador não resolve dois problemas reais — (1) não fica em segundo plano de verdade (depende de manter a aba/janela aberta), e (2) não isola áudio por aplicativo, então compartilhar "áudio do sistema" durante um jogo também vaza a voz da call do Discord pra quem assiste (eco). electron/

```
  build/icon.png          — copiado de public/icons/icon-512.png
  src/

```

### 15.1 Vídeo — funcionando, testado de ponta a ponta

A `main.js` carrega a URL de produção real (`https://sinal-app-stream.vercel.app`) — **não** duplica o site, é a mesma UI de sempre rodando dentro de uma casca nativa.

**Descoberta importante que mudou o plano original**: `setScreenShareEnabled()` do LiveKit tem bug conhecido no Electron (`DOMException: Not supported`), mas isso é evitável **sem mudar uma linha do `app.js`** — o Electron tem `session.setDisplayMediaRequestHandler()`, que intercepta o `getDisplayMedia()` padrão que o LiveKit já chama por baixo. Registrando esse handler na `main`, o `toggleShare()` do app.js funciona **exatamente como está hoje**, sem nenhum branch condicional "se Electron, faça diferente".

### 15.4 🔴 ACHADO CRÍTICO (2026-09-22, mesma sessão) — exclude-Discord NÃO funciona pra voz de call real

> **✅ Corrigido — ver §15.11.** Re-testado ao vivo, numa call real, depois da correção: silêncio total ao excluir o Discord. Mantido aqui como registro histórico do bug original.

**A v0.2.0 publicada NÃO cumpre a promessa principal.** Testes anteriores (§15.2/15.3) validaram o mecanismo de exclusão com áudio "genérico" (WAV tocado via processo PowerShell) — funcionava perfeitamente (diferença de 3x+ de amplitude). Mas isso nunca foi testado contra **voz de call real do Discord**. Quando testado de verdade (usuário numa call real, ao vivo, enquanto os testes rodavam):

- Excluir a raiz da árvore de processos do Discord (pid da vez, ex. `7448`): **amplitude praticamente idêntica** com e sem exclusão (`14343` vs `14095` de máxima — sem diferença real).
- Excluir especificamente o processo `--type=utility --utility-sub-type=audio.mojom.AudioService` do Discord (o suspeito óbvio, é literalmente o processo de áudio dele): **também não fez diferença** (`10018` de máxima, mesma faixa).

**Conclusão: nenhum dos processos visíveis na árvore do Discord (`Get-CimInstance Win32_Process -Filter "Name='Discord.exe'"`) é o dono da sessão WASAPI que renderiza a voz da call.** O mecanismo de exclude-por-processo (`PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`) funciona exatamente como documentado pela Microsoft — só que a voz da call parece não passar por nenhum desses PIDs.

**Hipótese não confirmada, próxima linha de investigação**: chamada de voz usa WebRTC (mesma tecnologia da própria Sinal), que costuma abrir a sessão de áudio no papel `eCommunications` do Windows, não `eConsole` (o que a nossa captura usa via `GetDefaultAudioEndpoint(eRender, eConsole)`). Mesmo que os dois papéis apontem pro mesmo dispositivo físico, não está confirmado que isso é irrelevante pro `PROCESS_LOOPBACK` — vale testar explicitamente contra o endpoint de `eCommunications` antes de qualquer outra teoria. Outras hipóteses não descartadas: o ADM (Audio Device Module) do WebRTC podendo abrir a sessão WASAPI num processo/thread que não aparece como "Discord.exe" na enumeração via `CreateToolhelp32Snapshot` (deveria aparecer, mas não confirmado com 100% de certeza), ou algum comportamento de mixagem/roteamento de áudio específico de chamada que o Windows trata diferente de reprodução normal.

**Impacto real**: o app funciona (vídeo, chat, moderação, segundo plano) e o áudio isolado funciona pra **áudio de app comum** (jogo, música, vídeo) — só **não** isola a voz da call, que é o motivo original de construir isso tudo. Quem baixar a v0.2.0 esperando não vazar mais a call pros espectadores **ainda vai ouvir a call**, igual sempre foi.

**Não repetir**: excluir a raiz da árvore do Discord (testado, não funciona pra voz), excluir o processo `audio.mojom.AudioService` do Discord especificamente (testado, não funciona). Próximo passo é investigar o papel `eCommunications` antes de tentar mais PIDs.

### 15.5 🔴 Segundo achado crítico — modo *include* não distingue janelas do MESMO app (2026-09-22)

> **⚠️ Re-testado depois da correção (§15.11/§15.12) — CONTINUA vazando, e não é bug.** Confirmado que é mesmo um limite estrutural do Windows/Chromium, não relacionado ao bug do PROPVARIANT: abriu duas janelas do Brave (vídeos diferentes), `GetWindowThreadProcessId` devolveu **o mesmo PID (a raiz do navegador) pras duas janelas** — Windows não expõe informação nenhuma que distinga qual janela pertence a qual PID, porque não existe distinção nenhuma, é a mesma instância/processo raiz pra ambas. Esse caso não tem solução possível via `PROCESS_LOOPBACK` — precisaria de outra técnica inteiramente (cabo de áudio virtual, API de captura por aba do próprio navegador). Ver §15.12 pra decisão sobre isso.

Relato real: usuário separou Instagram e YouTube em duas **janelas diferentes** do Brave, compartilhou só a janela do Instagram (modo *include*, ver §15.3) — **vazou o áudio do YouTube também**.

**Causa confirmada** (`Get-CimInstance Win32_Process -Filter "Name='brave.exe'"`): o Brave roda como **uma raiz só** (ex. PID `13488`) com N processos filhos `--type=renderer` — um por aba/janela — todos na mesma árvore. `getWindowProcessId(hwnd)` devolve o PID **dono da janela** (a raiz do navegador, `13488`), não o do renderer daquela aba especificamente — porque em navegadores multi-processo o HWND de nível superior pertence ao processo principal, não a um renderer individual. `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` captura a raiz **e toda a árvore** — ou seja, todas as abas/janelas do mesmo navegador, não só a escolhida.

**Isso não é um bug de implementação — é limite real da abordagem.** Isolamento por processo do SO enxerga só o nível de *processo*, não o nível de *aba/janela dentro do mesmo processo*. Pra isolar de verdade uma aba específica dentro do mesmo navegador, precisaria de uma API do próprio navegador (é exatamente pra isso que existe a captura de áudio por aba do Chrome/Chromium usada no "Compartilhar esta guia", que os navegadores implementam internamente antes de misturar tudo na saída de áudio do processo) — não dá pra replicar isso de fora, via WASAPI.

**Efeito prático**: o modo *include* (compartilhar uma janela específica) funciona bem pra isolar **um app de outro** (ex: um jogo, que roda como processo próprio, separado do Discord) — mas **não isola entre abas/janelas do mesmo navegador**, nem entre janelas de qualquer app que compartilhe um processo raiz comum (Discord também se enquadra: todas as janelas do Discord, se houvesse mais de uma, cairiam na mesma árvore).

**Não testado ainda**: se isolar coisas como duas janelas de apps *diferentes que sejam a mesma instalação* (ex: dois documentos abertos no mesmo Word) tem o mesmo problema — provável que sim, mesma causa raiz.

### 15.6 🔴 Terceiro achado crítico — vaza ENTRE APPS DIFERENTES também (2026-09-22, mesmo dia)

> **✅ Re-testado e confirmado corrigido (§15.12)** — cenário exato reproduzido de novo (Brave + Edge, vídeos diferentes, tocando ao mesmo tempo de verdade): excluir o Edge deixa o áudio do Brave passando normalmente (`18919` de amplitude, nada de silêncio), e incluir só um dos dois captura só aquele (`15007` só Edge, `1529` só Brave). **Isso derruba a explicação do §15.5.** Brave e Edge não compartilham processo raiz nenhum — são instalações e binários diferentes (`brave.exe` vs `msedge.exe`), árvores de processo totalmente independentes. Se o mecanismo de *include* estivesse filtrando por árvore de processo como documentado, o áudio do Edge nunca deveria aparecer.

**Estado real, juntando os três achados (§15.4, §15.5, §15.6)**:
- ✅ Funcionou uma vez, em teste controlado e sintético (`exclude-filter-test.mjs`): excluir um processo PowerShell recém-criado, tocando um WAV, reduziu a amplitude captada em mais de 3x.
- ❌ Não funcionou pra excluir a voz de uma call real do Discord (nem a raiz, nem o processo de áudio específico).
- ❌ Não funcionou pra isolar uma janela do Brave de outra janela do **mesmo** Brave.
- ❌ Não funcionou pra isolar uma janela do Brave do áudio de um processo **completamente diferente e não relacionado** (Edge).

**Isso não é mais "falta ajustar qual PID excluir"** — o padrão (1 caso sintético funcionando contra 3 casos reais falhando, inclusive um sem nenhuma relação de processo) sugere que a abordagem de isolar áudio por processo via `PROCESS_LOOPBACK` pode ter uma limitação bem mais fundamental do que o entendido até aqui nessa sessão, ou que o teste sintético que "funcionou" tinha algum fator não identificado que não se repete em cenários reais (diferença entre processo recém-criado vs processo já estabelecido e complexo, por exemplo — não confirmado, só hipótese).

**Decisão explícita**: não investigar mais isso nessa sessão (já muito longa). **Próxima sessão precisa tratar isso como uma investigação nova**, possivelmente reconsiderando a abordagem inteira (não só trocar qual PID mirar) — os candidatos de hipótese acumulados até aqui (papel `eCommunications` vs `eConsole`, timing de ativação antes/depois da sessão de áudio existir, isolamento por processo do Windows sendo fundamentalmente menos granular do que a documentação sugere pra apps complexos) precisam ser testados um a um, com tempo e cabeça fresca — não emendados no fim de uma sessão de 10+ horas.

**Mitigação recomendada pra próxima sessão, antes de resolver o problema de verdade**: dar a opção de **compartilhar sem áudio isolado nenhum** (ver §17) — hoje o app publica a track de áudio isolado automaticamente sempre que possível, sem escolha do usuário. Como a isolação está confirmadamente não-confiável, isso pode estar piorando a experiência (vazamento com falsa sensação de segurança) em vez de ser neutro. Uma opção de desligar deixa o comportamento pelo menos previsível.

### 15.7 Investigação nova (2026-09-22, sessão dedicada) — achado provável do causador real

Retomando como "investigação nova", com ferramentas melhores e uma fonte de áudio real e controlada disponível (vídeo do YouTube tocando no Brave, a pedido do usuário — muito melhor que o teste sintético original porque é um app complexo de verdade, tocando som de forma sustentada e sob controle).

**Ferramenta nova construída pra isso**: `list_audio_sessions()`, exportada pelo addon nativo (`electron/native/sinal-audio-loopback/src/lib.rs`) e testável via `node electron/test/list-audio-sessions.mjs`. Usa `IAudioSessionManager2`/`IAudioSessionEnumerator`/`IAudioSessionControl2::GetProcessId()` pra listar, ao vivo, TODA sessão de áudio ativa no endpoint padrão com o PID dono real — sem achismo sobre "qual processo deveria estar fazendo esse som". Achado imediato com ela: o PID que realmente segura a sessão de áudio ativa do Brave enquanto o YouTube tocava **não é a raiz (`brave.exe`) nem o renderer da aba** — é o processo utilitário dedicado `--type=utility --utility-sub-type=audio.mojom.AudioService` (filho direto da raiz), confirmado via `Get-CimInstance Win32_Process`. Isso bate exatamente com a arquitetura documentada do Chromium (áudio de TODAS as abas/janelas de uma instância passa por um único processo de serviço de áudio compartilhado) — ver achado de pesquisa abaixo.

**⚠️ Achado crítico, com teste controlado e real (não mais especulação)**: com o YouTube tocando de verdade no Brave, três testes em sequência:
1. `exclude` mirando o PID **exato e confirmado** do `audio.mojom.AudioService` do Brave (22472) → amplitude praticamente igual a não excluir nada (17206 vs 13544 de máxima — dentro da variação natural do próprio áudio, ou seja, **zero efeito de filtro**).
2. `include` mirando esse mesmo PID real (22472) → amplitude capturada (16903).
3. `include` mirando um **PID que nem existe** (999999) → amplitude capturada **praticamente idêntica** (17230).

O resultado 2 vs 3 é o mais importante: se o filtro por processo estivesse funcionando de qualquer forma minimamente correta, incluir um PID inexistente deveria capturar silêncio (não tem processo nenhum pra incluir), e incluir o PID real do Brave deveria capturar só o áudio dele. Os dois deram basicamente o mesmo resultado — **a captura está ignorando o parâmetro de processo completamente, tanto em include quanto em exclude, independente de qual PID é passado**. Não é mais "vaza áudio de alguns processos específicos" — parece que o filtro nunca esteve realmente ativo nessa implementação, e a captura sempre foi, na prática, loopback do sistema inteiro.

**Hipótese líder pra explicar isso (nova, bem fundamentada, ainda não confirmada com certeza)**: comparando nosso `activate_process_loopback()` com a amostra oficial da Microsoft (`microsoft/Windows-classic-samples`, `Samples/ApplicationLoopback/cpp/LoopbackCapture.cpp`, lida direto do repositório oficial nessa sessão) — as `StreamFlags` passadas pro `IAudioClient::Initialize` são **idênticas** nos dois códigos (`AUDCLNT_STREAMFLAGS_LOOPBACK | AUDCLNT_STREAMFLAGS_EVENTCALLBACK | AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`), então não é isso. A diferença real é **como o `IAudioClient` é obtido**: a amostra oficial (o único caminho que a Microsoft de fato valida pra esse recurso) ativa via `ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK, __uuidof(IAudioClient), &activateParams, this, &asyncOp)` — no dispositivo **virtual** especial `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`. O nosso código (trocado nessa mesma sessão anterior pra contornar o `E_INVALIDARG` nunca resolvido, ver §15.2) usa `IMMDevice::Activate()` num dispositivo **real** (`GetDefaultAudioEndpoint(eRender, eConsole)`). A documentação da Microsoft (lida com atenção total ao texto exato nessa sessão) diz só que `IMMDevice::Activate` "pode" aceitar esses parâmetros pra "configurar um audio client em modo loopback com um filtro de processo" — mas **não garante em lugar nenhum que o filtro é de fato aplicado da mesma forma nesse caminho síncrono/dispositivo real** que no caminho assíncrono/dispositivo virtual oficialmente validado. A ativação nesse caminho síncrono sempre "funciona" (nunca dá erro) — mas os testes de hoje sugerem fortemente que ela só entrega um loopback comum do dispositivo inteiro, ignorando silenciosamente `TargetProcessId`/`ProcessLoopbackMode`.

Isso reconta a história inteira de forma mais simples e coerente: o único teste que um dia "passou" (excluir um processo PowerShell sintético) pode muito bem ter sido coincidência de medição, e as três falhas reais documentadas em §15.4-15.6 fazem sentido porque **o filtro talvez nunca tenha estado realmente ativo** desde que a ativação foi trocada pra `IMMDevice::Activate()` — não é (só) uma limitação de app complexo, é possivelmente a técnica de ativação inteira não fazendo o que o nome sugere.

**Gotcha de processo descoberto e corrigido nessa sessão, relevante pra qualquer teste futuro**: `cargo build --release` recompila `target/release/sinal_audio_loopback.dll`, mas **NADA copia esse `.dll` pra `sinal_audio_loopback.node` automaticamente** — é preciso rodar `cp target/release/sinal_audio_loopback.dll target/release/sinal_audio_loopback.node` manualmente depois de cada build (ou o Electron/os testes continuam rodando o binário antigo, silenciosamente, sem aviso nenhum). Isso pode ter afetado testes de sessões anteriores sem ninguém perceber — vale ter isso em mente ao revisar resultados antigos. Considerar automatizar isso (script npm ou `build.rs`) numa próxima limpeza.

**Próximo passo real, não feito ainda**: voltar a investigar `ActivateAudioInterfaceAsync` + `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK` (o caminho oficialmente validado) com essa informação nova — o `E_INVALIDARG` documentado em §15.2 precisa ser resolvido de verdade dessa vez, em vez de contornado, porque o contorno (`IMMDevice::Activate` num device real) provavelmente nunca filtrou nada. Ainda não tentado retomar esse caminho nessa sessão — decisão explícita de reportar o achado pro usuário antes de investir mais tempo nisso.

### 15.8 Retomando o `E_INVALIDARG` (mesma sessão, logo em seguida) — reproduzido de novo, ainda não resolvido

Usuário pediu pra tentar mesmo assim. Reconstruído `examples/diag_default_activation.rs` e `examples/diag_immdevice_activate.rs` (que nem compilavam mais — precisavam da feature `implement` do crate `windows`, removida quando o código de produção migrou pra `IMMDevice::Activate()`; adicionada de volta em `Cargo.toml` só pros `examples/`, junto com um novo `examples/diag_async_process_loopback.rs` que reusa o completion handler já validado e aceita `pid`/`exclude` por argv).

**Testes rodados, todos contra o `IAudioClient` via `ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK, ...)` — o caminho oficial**:

2. Ativando o MESMO dispositivo virtual, mas com `pActivationParams = None` (sem blob nenhum) → **também `E_INVALIDARG`**. Resultado ambíguo (é bem possível que esse dispositivo virtual especificamente *exija* o blob pra saber o que fazer, então falhar sem ele pode ser o comportamento esperado, não um dado novo) — mas ao menos mostra que o erro não muda com ou sem o blob, então não é um problema de conteúdo/layout do blob especificamente.

- **Driver de áudio suspeito** (a máquina tem "AMD High Definition Audio Device" listado via `Win32_SoundDevice`, o que levantou a hipótese de ser áudio via GPU/HDMI com suporte incompleto a esse recurso) — descartado: o dispositivo de renderização PADRÃO de verdade (confirmado via `IMMDevice::OpenPropertyStore` + `PKEY_Device_FriendlyName`) é **"Fones de ouvido (High Definition Audio Device)"** — um codec HD Audio genérico/padrão, não algo exótico ligado à GPU.

**Estado real depois dessa segunda rodada**: `E_INVALIDARG` continua sem causa raiz identificada. Já foi comparado byte-a-byte com a amostra oficial da Microsoft E com um pacote npm de terceiro publicado (ambos falham igual nessa máquina — praticamente elimina "bug no nosso código"), e agora também eliminado driver de áudio exótico e build de Windows incomum como explicações fáceis. **Ambos os caminhos de ativação estão, na prática, quebrados** — o síncrono (`IMMDevice::Activate`) "funciona" mas não filtra nada (§15.7), o assíncrono/oficial (`ActivateAudioInterfaceAsync`) filtra corretamente (é a amostra validada da própria Microsoft) mas nunca ativa nessa máquina.

Próximos passos sugeridos, não tentados ainda: (a) procurar no Feedback Hub / Microsoft Q&A / GitHub por relatos de `E_INVALIDARG` especificamente na build 26200 do Windows 11 25H2 — pode ser regressão conhecida; (b) testar o mesmo binário/`examples/diag_async_process_loopback.rs` numa máquina Windows diferente (outro build/outro hardware de áudio), pra saber se é específico dessa instalação ou geral; (c) considerar abrir um relatório de bug pra Microsoft, já que o comportamento diverge da documentação oficial e da amostra oficial deles mesmos.

**Consequência prática imediata, reforçada**: como os dois caminhos de ativação estão comprovadamente quebrados (um silencioso, um com erro), a opção de **compartilhar sem áudio isolado nenhum** (§17) deixou de ser só "recomendada" e passa a ser **necessária** — hoje o app tenta publicar áudio isolado sempre que possível e, na prática, isso nunca funcionou de verdade desde que foi implementado.

### 15.9 Pesquisa externa (agente dedicado, mesma sessão) — a API funciona pra outras pessoas; caminho alternativo viável identificado

Pedido explícito do usuário: pesquisar fundo (fóruns, Reddit, GitHub, artigos) antes de desistir do áudio com isolamento de verdade. Resumo do relatório completo (fontes linkadas abaixo):

- **Ninguém mais relatou esse `E_INVALIDARG` especificamente** nessa combinação de API — não é um bug amplamente conhecido/documentado.
- **Achado mais importante**: existe um projeto real, em produção, resolvendo **exatamente o mesmo problema** (excluir a árvore de processos de um cliente tipo-Discord pra evitar eco da call durante compartilhamento de tela) — [`thomas-quant/wasapi-loopback`](https://github.com/thomas-quant/wasapi-loopback), criado pro [GoofCord issue #46](https://github.com/Milkshiift/GoofCord/issues/46) (mesmo sintoma: "pessoas ouvem a própria voz na transmissão"). Usa o MESMO caminho oficial (`ActivateAudioInterfaceAsync` + `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`) que dá `E_INVALIDARG` pra gente. O plugin `win-capture-audio` do OBS também usa a mesma API sem workaround visível. **Isso é evidência forte de que a API funciona de verdade em máquinas reais** — o problema provavelmente é específico dessa instalação/máquina de dev, não uma falha geral da API ou do Windows 25H2.
- **Próximo passo mais barato e decisivo, ainda não feito**: testar o mesmo binário (`examples/diag_async_process_loopback.rs`) numa máquina Windows diferente. Se funcionar lá, o `E_INVALIDARG` é peculiaridade dessa máquina específica e não trava o projeto pra ninguém além do ambiente de dev atual.
- **Caminho alternativo, madura e comprovada por terceiros, caso o `PROCESS_LOOPBACK` continue não funcionando**: em vez de filtrar por PID na captura, **redirecionar a saída do app-alvo (ex: Discord) pra um dispositivo de áudio virtual** via `IPolicyConfig2::SetPerAppDefaultEndpoint` (API COM não-documentada oficialmente, mas extremamente estabelecida — é o mecanismo por trás do "Mixer de volume" nativo do Windows, usado por [EarTrumpet](https://github.com/File-New-Project/EarTrumpet/blob/dev/EarTrumpet/Interop/MMDeviceAPI/IPolicyConfig.cs), SoundVolumeView, nircmd e o projeto open-source [Audio Router](https://github.com/audiorouterdev/audio-router)) — e então capturar **loopback comum, sem filtro nenhum**, desse cabo virtual (só o app redirecionado chega lá). Isso elimina de vez a dependência do `PROCESS_LOOPBACK`/`ActivateAudioInterfaceAsync`, E resolve de graça os problemas de granularidade dos §15.5/15.6 (o redirecionamento por app do Windows já opera no processo raiz, é o que a UI nativa faz com sucesso pra apps multi-processo há anos).
  - **Driver a usar**: [VB-CABLE](https://vb-audio.com/Cable/) — gratuito pra uso pessoal, **assinado oficialmente** (não precisa de test-signing), cada pessoa instala direto do site oficial. **Não** usar [VirtualDrivers/Virtual-Audio-Driver](https://github.com/VirtualDrivers/Virtual-Audio-Driver) (open-source) — ele exige Windows Test-Signing Mode, que o **BattlEye recusa rodar** ("Failed to initialize BattlEye Service: Windows Test-Signing Mode not supported") — inviável pra um grupo que joga.
  - **Custo real**: fricção de instalação (cada amigo que quiser áudio isolado instala o VB-CABLE uma vez, não dá pra embutir silenciosamente sem driver assinado próprio) — mas usando peças individualmente maduras e testadas em produção por terceiros há anos, ao contrário de continuar caçando uma causa raiz não identificada.

**Recomendação do próprio relatório, nessa ordem**: (1) testar em outra máquina primeiro — barato e decisivo; (2) se funcionar lá, shippar como está e tratar o `E_INVALIDARG` como peculiaridade local; (3) se falhar igual em outra máquina, migrar pra VB-CABLE + `IPolicyConfig2` + loopback clássico. Nenhuma tentativa de implementação começada ainda — decisão de qual caminho seguir fica pra quando o teste em outra máquina acontecer.

### 15.11 ✅ RESOLVIDO DE VERDADE (2026-09-22, manhã seguinte) — causa raiz achada e corrigida

**Teste em outra máquina** (§15.9/§15.10, item 1 do roadmap): rodado o `.exe` standalone do diagnóstico no notebook do usuário (Windows 10 22H2, build 19045, hardware de áudio Realtek — completamente diferente da máquina de dev). **`E_INVALIDARG` idêntico.** Isso fechou a questão: não é peculiaridade de uma máquina, é um bug de verdade no nosso código, reproduzível em qualquer lugar.

**Causa raiz encontrada** comparando campo a campo com [thomas-quant/wasapi-loopback](https://github.com/thomas-quant/wasapi-loopback) (o projeto real, em produção, achado na pesquisa do §15.9): a função que a gente usava pra montar o `PROPVARIANT` — `InitPropVariantFromBuffer` — **não cria um PROPVARIANT do tipo `VT_BLOB`**. A documentação da própria função diz, literalmente: *"Creates a **VT_VECTOR | VT_UI1** propvariant."* Só que a API de ativação de áudio (`ActivateAudioInterfaceAsync`/`IMMDevice::Activate` pra `AUDIOCLIENT_ACTIVATION_PARAMS`) exige `VT_BLOB` — é isso que a amostra oficial da Microsoft em C++ monta na mão (`activateParams.vt = VT_BLOB`), e é isso que a documentação do `IMMDevice::Activate` pede explicitamente pro caso do `DIRECTX_AUDIO_ACTIVATION_PARAMS` (mesmo mecanismo de blob).

**Ou seja**: a gente mandava pro Windows um PROPVARIANT do tipo errado, **toda vez, em toda máquina**, desde que esse código foi escrito. O `E_INVALIDARG` nunca foi um bug misterioso do Windows nem uma peculiaridade de hardware/driver/build — era o Windows **corretamente rejeitando** um parâmetro malformado. E o caminho síncrono (`IMMDevice::Activate`, usado desde §15.2) tinha o mesmíssimo problema — só que, nesse caminho, o Windows não valida o `vt` com o mesmo rigor e silenciosamente ignora o filtro de processo inteiro, caindo pra loopback comum do sistema todo (explica de uma vez §15.7: por que "funcionava" sem erro mas nunca filtrava nada).

**Correção**: construir o `PROPVARIANT` na mão, igual à amostra oficial e ao thomas-quant — usando o tipo "cru" `windows::core::imp::PROPVARIANT` (sem `Drop`, pra não correr risco de `PropVariantClear` tentar `CoTaskMemFree` num ponteiro de stack e corromper a heap), setando `vt = VT_BLOB.0` e o campo `blob` direto. Voltado a ativar via `ActivateAudioInterfaceAsync` no dispositivo virtual (`VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`) — o caminho oficial/validado pela Microsoft — em vez do `IMMDevice::Activate()` num device real. Implementado em `activate_process_loopback()` (`src/lib.rs`), com um completion handler novo (`ActivationCompletionHandler`, `#[implement(IActivateAudioInterfaceCompletionHandler, IAgileObject)]`) baseado no mesmo padrão já validado nos `examples/diag_*.rs`. `windows-core` virou dependência direta (não só de dev) — a macro `#[implement]` precisa dela resolvível na raiz do crate. Todo o resto do pipeline (event handle, `IAudioCaptureClient`, loop de leitura de buffer) **não mudou nada** — só a ativação.

**Testado de verdade, não só "compilou"**:
1. `examples/diag_async_process_loopback.rs` corrigido → `GetActivateResult hr = HRESULT(0x00000000)` (S_OK) — ativação funciona, pela primeira vez, nessa máquina.
2. Correção portada pro `lib.rs` de produção, addon recompilado. Teste de captura real contra o processo de áudio confirmado do Brave (vídeo tocando):
   - `exclude(PID do Brave)` → `maxAmp: 1` (silêncio — era a única fonte tocando, bate certinho).
   - `include(PID do Brave)` → `maxAmp: 7152` (captura o áudio de verdade).
   - `include(PID inexistente)` → `maxAmp: 1` (silêncio — antes disso capturava tudo igual, ver §15.7).
3. **O teste mais importante — call de voz real do Discord, ao vivo, com o usuário falando**: `exclude(PID raiz do Discord)` → `maxAmp: 1` (silêncio total) vs sistema inteiro sem excluir nada → `maxAmp: 13369` (voz capturada normalmente). **Esse era exatamente o cenário que falhava em §15.4** (nem excluir o processo exato de áudio do Discord resolvia antes) — agora funciona perfeitamente.

**Como isso fecha as três falhas documentadas em §15.4-15.6**: as três tinham a MESMA causa raiz (filtro nunca aplicado de verdade, independente de qual PID/modo era passado) — não eram três bugs de granularidade/timing/arquitetura diferentes como se chegou a suspeitar, era um único bug de tipo de dado na camada de ativação. §15.4 (Discord em call) confirmado resolvido com teste ao vivo acima. §15.5 e §15.6 re-testados logo em seguida — ver §15.12.

### 15.12 Re-teste dos outros dois cenários originais (2026-09-22, logo em seguida) — cross-app resolvido, multi-janela é limite estrutural (não bug)

**Instalador reconstruído** com a correção (`cd electron && npm run dist`) — `dist/Sinal-Setup-0.3.0.exe` + `latest.yml` + `.blockmap` gerados, addon nativo confirmado como o build corrigido (checado por tamanho/timestamp do `.node` empacotado). Ainda **não publicado** como release no GitHub — só gerado local até aqui.

**§15.6 (cross-app, Brave vs Edge) — reproduzido de novo e confirmado 100% resolvido**: abriu Brave e Edge simultaneamente, cada um com um vídeo do YouTube diferente tocando de verdade.
- `include(só Edge)` → `15007` de amplitude máxima (áudio real do Edge).
- `include(só Brave)` → `1529` (áudio real do Brave, vídeo mais baixo).
- `exclude(Edge)` → `18919` — **nada de silêncio**: o áudio do Brave (+ o resto do sistema) continua passando normalmente enquanto só o Edge fica de fora. Exatamente o comportamento correto — isolamento seletivo entre dois apps completamente diferentes, funcionando de verdade.

**§15.5 (multi-janela, mesmo navegador) — reproduzido de novo, CONTINUA vazando, mas agora com causa raiz 100% confirmada e é permanente**: abriu duas janelas do Brave (vídeos diferentes), enumerou as janelas de verdade via `EnumWindows`/`GetWindowThreadProcessId` (não só `Get-Process`, que só mostra uma janela por processo e escondia o problema) — **as duas janelas devolveram o mesmíssimo PID (`16304`)**, a raiz do Brave. Confirmado também que o `getWindowProcessId()` do nosso próprio addon (usado de verdade no `main.js`) devolve esse mesmo PID pras duas. **Não é um bug pra corrigir — é a arquitetura do Chromium**: todas as janelas de uma mesma instância do navegador são donas do mesmo processo raiz pro sistema operacional; não existe informação nenhuma no Windows que diferencie "janela A" de "janela B" da mesma instância. Bate exatamente com a pesquisa externa do §15.9 (Chromium centraliza áudio de todas as janelas/abas num único processo de serviço de áudio compartilhado por instância).

**Consequência prática**: compartilhar **uma janela específica** de um navegador com várias janelas abertas ainda vaza o áudio das outras janelas *desse mesmo navegador* — mas não vaza mais o áudio de **outros apps** (Discord, outro navegador, jogos, etc.), que é o caso que mais importa (era o motivo original de construir isso). Se algum dia quiser resolver o caso de multi-janela também, precisaria de uma abordagem diferente (cabo de áudio virtual + redirecionamento por app, já documentado em §15.9 — mas resolveria por app inteiro, não por janela específica dentro do mesmo navegador; ou uma extensão de navegador usando `tabCapture`/`setSinkId`, mencionada na pesquisa). Não é prioridade agora dado que o caso principal (Discord + apps diferentes) já funciona.

**Decisão do usuário (2026-09-22)**: multi-janela do mesmo navegador não é caso de uso relevante pro grupo ("quem usa duas janelas do mesmo browser") — não vale investir em resolver isso. Fechado como limitação conhecida e aceita, não como pendência.

### 15.13 Achado novo, real, num teste ao vivo com a galera: o próprio Sinal vazava o próprio áudio (self-leak)

Reportado pelo usuário durante o teste real de produção do §15.12: com **dois participantes compartilhando ao mesmo tempo**, o áudio de um vazava na transmissão do outro. Não é o mesmo bug do §15.4/§15.6 (esses eram sobre Discord/outros apps) — **causa diferente**.

**Causa raiz confirmada** (checado ao vivo: `Sinal.exe` tinha uma sessão de áudio ATIVA no momento, via `list_audio_sessions`): no modo "compartilhar tela inteira", `determineAudioTarget()` só excluía o Discord — nunca o próprio Sinal. Se a Pessoa B está **assistindo** a transmissão da Pessoa A (ouvindo o jogo dela pelas caixas de som, via um `<video>` normal do LiveKit) **enquanto também compartilha a própria tela**, a captura WASAPI de B pega "tudo, menos o Discord" — o que inclui o que o **próprio Sinal** está tocando (a transmissão de A). O áudio de B sai com uma cópia (com delay de rede) do que B estava ouvindo de A.

**Restrição técnica que motivou a solução**: `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS.TargetProcessId` é um único PID — não dá pra excluir Discord E o próprio Sinal numa chamada só. Pesquisa externa (agente dedicado) confirmou que produtos reais com o mesmo problema estrutural (Parsec — recomenda roteamento pra dispositivo secundário; Backspace — teve o bug idêntico, corrigido excluindo a si mesmo via flag do Electron; GoofCord — exclui só a si mesmo, não tem o caso "excluir dois"; OBS — usa modo *include* por processo específico) **nenhum resolve com "cancelamento de eco mágico"** — a ideia de expor a captura como microfone virtual e deixar o `echoCancellation` do Chromium cancelar sozinho foi pesquisada e **descartada**: o AEC do Chromium só cancela o que ele mesmo sabe que está renderizando (elementos de mídia da própria página), não tem acoplamento nenhum com uma captura de sistema externa.

**Solução implementada (2026-09-22/23, mesma sessão)**: em vez de "excluir Discord" (um alvo só), o modo "compartilhar tela inteira" passou a funcionar por **inclusão dinâmica multi-fonte**:
1. A cada 2s (`MULTI_SCAN_INTERVAL_MS`), `scanAudioSources()` (`electron/src/main.js`) chama `list_audio_sessions()` pra descobrir tudo que está fazendo som agora.
2. Tira da lista, sempre, Discord e o próprio `Sinal.exe` (`isEligibleSource()`) — não é escolha do usuário, nunca aparecem no checklist.
3. Pra cada processo elegível ainda não capturado, abre um `AudioLoopback` novo em modo **incluir** (`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`) — múltiplas instâncias nativas rodando ao mesmo tempo, uma por processo, sem conflito entre si (testado, ver abaixo).
4. Cada captura manda seus pedaços de PCM marcados com o PID de origem (`{pid, buf}`) via IPC — a **mistura de verdade acontece do lado do renderer**, em `createElectronIsolatedAudioTrack()` (`public/app.js`): uma fila por PID, somadas amostra a amostra no `onaudioprocess`, com *clamp* em ±1.0 (evita estourar quando várias fontes tocam alto ao mesmo tempo).
5. Reavalia sozinho — um app que abre DEPOIS que a transmissão já começou entra automaticamente no próximo scan; um app que fecha sai sozinho.
6. **Bônus pedido pelo usuário**: checklist visual (`#audioSourcesPanel`, abaixo dos controles) com um checkbox por app detectado — desmarcar um app chama `toggleAudioSource(pid, exeName, false)`, que para a captura dele e lembra a escolha (por nome de exe, não PID, já que PID muda se o app reiniciar) até a transmissão atual acabar. Painel só aparece no modo "tela inteira" (no modo "compartilhar uma janela" nunca dispara — aquele modo já isola um processo só sozinho, sem precisar de multi-fonte, ver §15.12).

O modo "compartilhar uma janela específica" **não muda nada** — continua usando `AudioLoopback` único em modo incluir, como já validado em §15.12.

**Testado, mas não 100% ao vivo na interface real** (Claude não consegue clicar no seletor nativo de tela do Windows/picker.html):
- ✅ **Captura nativa multi-fonte, de verdade**: script isolado (`electron/test/multi-source-test.mjs`) rodou o mesmo algoritmo de `scanAudioSources()` fora do Electron, com Discord, Sinal, Brave e Edge todos tocando som ao mesmo tempo de verdade — confirmado: Discord e Sinal nunca apareceram na lista; Brave e Edge foram capturados **simultaneamente, sem conflito** (`maxAmp` real e não-nulo nos dois ao mesmo tempo); um processo novo (o próprio script Node) foi detectado e adicionado automaticamente no scan seguinte, sem reiniciar nada.

Remover uma fonte (`onAudioSourceRemoved`) fez a saída voltar a exatamente o valor da fonte restante, sem resquício. Duas fontes somando mais que 1.0 clamparam certinho em `1.0`. O painel (`renderAudioSourcesPanel`) mostrou os checkboxes certos (marcado/desmarcado batendo com `enabled`), escondeu com lista vazia, e o clique no checkbox chamou `toggleAudioSource` com os parâmetros certos.

**Corrigido de brinde nessa mudança**: um vazamento de listener de IPC pré-existente — cada início de compartilhamento registrava `onAudioChunk`/`onAudioSources`/`onAudioSourceRemoved` de novo sem nunca remover os antigos (`preload.js`). ### 15.14 🔴 Achado crítico real, no MESMO dia: bug de threading do COM fazia o painel falhar de forma intermitente

Segundo teste do usuário (mesmo instalador v0.3.1, mesma máquina): compartilhou a tela inteira de novo, áudio ligado, confirmou "tela inteira" no seletor — **painel não apareceu**. Contradição direta com o teste anterior que tinha "fechado". Pedido pra rodar `npm start` (mostra os logs do processo principal no terminal) revelou o erro de verdade:

```
[sinal-audio] listAudioSessions() falhou: Error: CoInitializeEx: Não é possível
alterar o modo de thread depois de o mesmo estar definido. (0x80010106)
```

**Causa raiz**: `list_audio_sessions()` (`src/lib.rs`) chamava `CoInitializeEx(None, COINIT_MULTITHREADED)` incondicionalmente, assumindo que era a primeira coisa a inicializar COM naquela thread — verdade no `electron/test/multi-source-test.mjs` (roda em Node puro, thread "limpa"), **falso dentro do Electron de verdade**: `scanAudioSources()` é chamado direto na thread principal do processo Electron, que é a MESMA thread que o Chromium já inicializa como COM apartment **single-threaded (STA)** logo na largada, antes de qualquer código nosso rodar. Pedir `COINIT_MULTITHREADED` (MTA) numa thread que já tem um modelo diferente dá `RPC_E_CHANGED_MODE` (`0x80010106`) — Windows não deixa trocar o modelo de uma thread já inicializada.

**Por que foi intermitente, não sempre**: `IAudioLoopback`/`activate_process_loopback` (a captura em si) roda numa thread NOVA, dedicada (`std::thread::spawn`), que ninguém mais tocou — `CoInitializeEx(MULTITHREADED)` lá sempre é a primeira chamada, nunca conflita. Só `list_audio_sessions()` roda direto na thread principal compartilhada com o Chromium — o resultado depende de quando exatamente ela é chamada em relação a outras inicializações internas do Electron, por isso "funcionou uma vez, falhou a próxima" no mesmo instalador, mesma máquina.

**Corrigido**: `list_audio_sessions()` agora trata `RPC_E_CHANGED_MODE` como "COM já tá pronto nessa thread, só não fomos nós que inicializamos" em vez de erro fatal — segue em frente sem chamar `CoUninitialize()` no final (não é referência nossa pra soltar). `IMMDeviceEnumerator`/`IAudioSessionManager2` funcionam normalmente em STA ou MTA, então isso não perde funcionalidade nenhuma.

**Verificado de verdade, na thread principal real do Electron** (não só no teste isolado fora dele, que nunca teria pego esse bug): novo `electron/test/com-threading-test.mjs`, rodado via `npx electron test/com-threading-test.mjs` (não `node`) — chama `listAudioSessions()` direto no `app.whenReady()` do processo principal, duas vezes seguidas (simulando o scan periódico). As duas chamadas funcionaram sem erro, com sessões reais detectadas.

**Lição pra próximas vezes**: qualquer teste de código que compartilha COM/threading com o host precisa rodar *dentro* do ambiente real (Electron), não só isolado em Node puro — um teste "passando" fora do host não garante nada sobre conflitos de inicialização que só o host real provoca. `electron/test/multi-source-test.mjs` continua útil (valida a lógica de scan/captura em si), mas não substitui testar dentro do Electron pra esse tipo de bug.

**✅ Confirmado pelo usuário, na interface real, `desktop-v0.3.2` (2026-09-22)**: compartilhou a tela inteira com áudio ligado — painel apareceu com `claude.exe`, `brave.exe` e `steam.exe` detectados e marcados, Discord e o próprio Sinal corretamente fora da lista. Fecha o modo multi-fonte de vez: causa raiz achada, corrigida, e validada na prática, não só em teste isolado.

## 16. Como atualizar o app desktop já instalado

**✅ Implementado (2026-09-22, v0.3.0)**: `electron-updater` (`electron/src/main.js`, função `setupAutoUpdater()`) checa o GitHub Releases sozinho — 10s depois de abrir, e depois a cada 4h enquanto o app fica rodando na bandeja. Baixa a atualização em segundo plano (`autoDownload = true`) e só reinicia com confirmação explícita (diálogo "Reiniciar agora" / "Depois" via `dialog.showMessageBox`) — nunca troca a versão sem avisar. Só roda em build empacotado (`app.isPackaged`); em dev (`npm start`) fica sem efeito, sem erro.

**Config em `electron/package.json`** (`build.publish`): provider `github`, `owner: Pedr030`, `repo: sinal-app`, `tagNamePrefix: "desktop-v"` — casa com a convenção de tag já usada (`desktop-v0.1.0`, `desktop-v0.2.0`, ...). O updater lê a *release* mais recente não-draft/não-prerelease do repo via API pública do GitHub — como o repo é público, não precisa de token nenhum embutido no app pra isso (só quem *publica* uma release precisa de `GH_TOKEN`, e continuamos publicando manualmente via `gh`, não via `electron-builder --publish always`, de propósito — mantém controle/confirmação antes de qualquer release ir ao ar).

**⚠️ Pegadinha real, já corrigida**: o nome padrão do instalador NSIS (`${productName} Setup ${version}.${ext}` → `Sinal Setup 0.3.0.exe`, com espaços) quebra o auto-update de um jeito sutil e conhecido (bug documentado no próprio electron-builder): o GitHub troca espaço por **ponto** ao guardar o asset (`Sinal.Setup.0.3.0.exe`), mas o `electron-updater` troca espaço por **hífen** ao montar a URL de download a partir do `latest.yml` (`Sinal-Setup-0.3.0.exe`) — nenhum dos dois bate, e o download do update daria 404 silencioso pra todo mundo. Corrigido fixando `build.nsis.artifactName: "Sinal-Setup-${version}.${ext}"` (sem espaço nenhum, então não tem o que o GitHub ou o updater precisem trocar — os três nomes — local, GitHub, e o que o `latest.yml` pede — ficam idênticos). Confirmado gerando o build localmente: `dist/latest.yml` aponta pra `Sinal-Setup-0.3.0.exe`, que é exatamente o nome do `.exe` gerado.

**Processo de release a partir de agora** (repete pra cada versão nova do desktop):
1. Bump `"version"` em `electron/package.json`.
2. `cd electron && npm run dist` (roda `electron-builder --publish never` — nunca publica sozinho, só gera os arquivos em `electron/dist/`).
3. Confere que saíram os 3 arquivos: `Sinal-Setup-X.Y.Z.exe`, `Sinal-Setup-X.Y.Z.exe.blockmap`, `latest.yml`.
4. `gh release create desktop-vX.Y.Z electron/dist/Sinal-Setup-X.Y.Z.exe electron/dist/Sinal-Setup-X.Y.Z.exe.blockmap electron/dist/latest.yml --title "Sinal Desktop vX.Y.Z" --notes "..."` — **os três arquivos precisam ir juntos**, não só o `.exe`: sem o `latest.yml` o updater não descobre que existe uma versão nova, e sem o `.blockmap` ele ainda funciona mas sem o download diferencial (baixa o instalador inteiro de novo em vez de só o pedaço que mudou).
5. **As notas da release sempre começam com "## O que baixar" + "## O Windows vai avisar..."** (pedido do usuário, 2026-09-23):
   - **"## O que baixar"**: depois de notar que a página de release lista os 3 arquivos sem explicar qual é pra baixar de verdade — algo como "Baixe **Sinal-Setup-X.Y.Z.exe** e rode. Os outros dois arquivos (`latest.yml`, `.exe.blockmap`) não são pra baixar, servem só pro app já instalado se auto-atualizar sozinho." Quem chega na página de releases direto (ex: pelo botão "Baixar Sinal Desktop" do site, ver §24) não sabe de antemão qual arquivo é o certo.
   - **"## O Windows vai avisar..."**: o instalador NÃO é assinado com certificado de code-signing pago (não faz sentido gastar nisso num projetinho sem fins comerciais pra um grupo de amigos — mesma linha do "não sugerir opção paga" já estabelecida) — então o SmartScreen do Windows quase certamente mostra a tela "Editor desconhecido" pra quem roda o instalador pela primeira vez. Pedido explícito do usuário: não só avisar que isso vai acontecer, mas **explicar o motivo e passar segurança** — texto padrão: explica que é só por causa do certificado pago (não é sinal de vírus), como prosseguir ("Mais informações" → "Executar assim mesmo"), e menciona que o repositório é público pra quem quiser conferir o código antes de rodar. Ver o texto usado na v0.3.5 como referência/modelo pras próximas releases.

**⚠️ Quem já tem v0.1.0 ou v0.2.0 instalado NÃO recebe esse update automático** — essas releases foram publicadas antes do `electron-updater` existir no app (sem `latest.yml`, sem o código do updater rodando). ## 18. "Clique pra assistir" (igual ao Discord) — 2026-09-22

## 23. Links de convite abrindo o app desktop instalado (protocolo `sinal://`)

**Pedido do usuário**: o webhook do Discord (§13) já posta o link de convite (`?sala=CODIGO`) quando alguém cria sala — mas clicar nesse link sempre abre no navegador, mesmo pra quem já tem o app desktop instalado.

**Implementado**: protocolo customizado `sinal://`, no mesmo espírito do que Discord/Spotify/Zoom usam — mas sem trocar o link do webhook (continua `https://` normal, universal, funciona pra qualquer um mesmo sem o app instalado).

- **`electron/src/main.js`**: `app.setAsDefaultProtocolClient('sinal')` registra o protocolo. `app.requestSingleInstanceLock()` (novo, não existia antes) garante que clicar o link com o app já aberto só foca a janela existente em vez de abrir um processo novo (importante especialmente pelo áudio isolado nativo — duas instâncias capturando ao mesmo tempo seria problema). Link no formato `sinal://join?sala=CODIGO`. Duas entradas:
  - **App fechado**: o Windows passa a URL como argumento de linha de comando do primeiro lançamento — `process.argv` é checado antes de criar a janela, que já abre direto em `SINAL_URL/?sala=CODIGO` em vez de abrir vazia.
  - **App já aberto**: evento `second-instance` (novidade do lock de instância única) recebe a URL, foca/restaura a janela e navega ela pra sala.
- **`public/app.js`** (`setupOpenInApp()`, chamada no `DOMContentLoaded`): só roda fora do Electron (`!window.sinalElectron?.isElectron`) e só quando a URL tem `?sala=` (ou seja, só faz sentido pra quem chegou via link de convite). Tenta navegar pra `sinal://join?sala=CODIGO` — **sem UI própria nenhuma**: o navegador (Chrome/Edge) já mostra sozinho um prompt nativo "Abrir Sinal? ... [x] Sempre permitir ... [Abrir Sinal]/[Cancelar]" quando detecta o protocolo registrado, com a própria opção de "lembrar" embutida — não precisa duplicar isso com banner/checkbox custom. **Primeira versão tinha um banner próprio** ("Tem o app instalado? [Abrir no app] [x] Sempre abrir automaticamente") — usuário testou, achou desnecessário (o prompt nativo do navegador já resolve sozinho) e pediu pra simplificar; banner removido, sobrou só a tentativa de navegação direto no carregamento da página.
- Se o protocolo não estiver registrado (app não instalado), a tentativa de navegação só falha em silêncio — a pessoa segue pro formulário normal da página sem nenhum travamento/aviso feio.

**Testado**: lógica isolada no navegador (mesmo padrão de mock já usado no projeto) — sem `?sala=` ou dentro do Electron não tenta nada; com `?sala=` no navegador normal tenta a navegação e a página continua funcionando normalmente mesmo sem o protocolo registrado (ambiente de teste não tem). O prompt nativo do navegador (imagem real) foi confirmado pelo usuário rodando contra o site de produção de verdade, com o instalador v0.3.5 já instalado — a checagem de correspondência do domínio/protocolo do Windows já reconheceu o Sinal como app associado. `node --check` limpo em `main.js`/`app.js`. **Ainda não confirmado o fim do fluxo** (clicar "Abrir Sinal" no prompt realmente abre o app e navega pra sala certa via `second-instance`/argv).

**Precisa de instalador novo** — mudança em `main.js` (registro de protocolo + lock de instância única), só publicar no Vercel não ativa isso pra quem já tem o app instalado.

## 26. Atalho global de compartilhar + aba de configurações

**Pedido do usuário**: atalho de teclado global pra compartilhar/parar sem precisar focar a janela (idea cogitada em §19). Pedido explícito do usuário: só guardar o necessário pra essa feature ali, nada pessoal (nome, sala, etc — isso continua só no `localStorage` do site, sem mudança).

**Implementado**:
- **`main.js`**: `loadSettings()`/`saveSettings()` (JSON, fallback pro padrão se corrompido/ausente). `registerShareShortcut()` — desregistra o atalho anterior e registra o novo conforme `appSettings`, reaproveitada tanto no boot quanto a cada mudança via settings (rebind não pode deixar o atalho velho registrado junto). `ipcMain.handle('sinal:get-settings'/'sinal:set-settings')` — o `set` já persiste, re-registra o atalho, e devolve se o registro deu certo (pra UI avisar se a combinação nova conflita com outro programa). Flag `skipPickerOnce` + `ipcMain.on('sinal:request-quick-share')`: quando setada, a próxima chamada de `getDisplayMedia` (dentro de `setDisplayMediaRequestHandler`) pula `showSourcePicker()` e escolhe a tela primária direto (casada pelo `display_id` contra `screen.getPrimaryDisplay()`, não só a primeira da lista — `desktopCapturer` não garante ordem).
- **`preload.js`**: `getSettings`/`setSettings` (via `invoke`, assíncronos) e `requestQuickShare` (`send`, fire-and-forget).
- **`public/index.html`/`style.css`**: ícone de engrenagem no cabeçalho (só dentro do Electron, mesmo padrão de `#installBtn`/`#downloadDesktopBtn` mas ao contrário — só aparece em `body.electron-app`) abre um painel modal (`#settingsOverlay`) com: liga/desliga o atalho, mostra a combinação atual + botão "Gravar novo atalho", e o checkbox de tela inteira direto.
- **`public/app.js`**: `setupSettingsPanel()` — carrega settings via IPC, aplica na UI, cada mudança já salva na hora (sem botão "salvar" separado, mesmo padrão instant-apply do resto do app). Captura de nova combinação: escuta o próximo `keydown` com pelo menos um modificador (Ctrl/Alt/Win) + uma tecla final (letra/número/F1-F24) — Esc cancela. `setupGlobalShareShortcut()` atualizado: antes de chamar `toggleShare()`, checa se é um COMEÇO de compartilhamento (não tem publicação de tela ainda) e se a preferência de tela inteira tá ligada — se sim, chama `requestQuickShare()` primeiro.

**Testado**: `node --check` limpo em `main.js`/`preload.js`/`app.js`. Toda a lógica do lado do site testada via mock de `window.sinalElectron` no navegador (mesmo padrão já usado no projeto) — painel abre/fecha, mostra o estado certo, toggle de cada checkbox persiste (via IPC mockado), rebind captura a combinação corretamente e atualiza a UI, erro de registro aparece quando o `main.js` mockado devolve falha, e a lógica de `requestQuickShare` dispara certinho só quando é início de compartilhamento (não ao parar) e só com a preferência ligada — confirmado com objeto de sala falso, testando os dois cenários (compartilhando/não compartilhando). **Não testado ainda com o Electron real rodando** (registro de atalho de verdade, captura de tela pulando o seletor de verdade, persistência do JSON entre reinicializações) — precisa de instalador novo pra isso.

## 28. Áudio isolado atrasando + diagnóstico de vídeo "farinhado" (2026-09-28)

**Bug relatado pelo usuário, assistindo a tela de um amigo**: áudio atrasado em relação ao vídeo — "vai aumentando, por um instante normaliza e repete o ciclo".

**Causa**: a fila de áudio isolado (`createElectronIsolatedAudioTrack()` em `public/app.js`, lado de quem compartilha pelo app desktop) aceitava até **2s** acumulados por fonte, e só zerava tudo quando estourava. Como a reprodução consome exatamente em tempo real, qualquer sobra acumulada (engasgo da thread principal, IPC chegando em rajada) nunca era recuperada — virava atraso permanente, subindo até 2s, zerando e recomeçando. Exatamente o ciclo relatado.

**Corrigido**:
- Fila agora fica perto de ~100ms (`TARGET_QUEUED_FRAMES = 4800`): passou de ~250ms (`MAX_QUEUED_FRAMES = 12000`), `trimToTarget()` corta só o excesso mais antigo de volta pro alvo — atraso sempre limitado, ao custo de um pulinho curto ocasional em vez de 2s de atraso.
- `ScriptProcessor` de 4096 pra 2048 frames (~85ms → ~43ms de latência fixa). **Contrapartida registrada**: roda na thread principal, então engasgo dela maior que ~43ms vira estalo audível. Se estalos aparecerem com frequência, voltar pra 4096 e subir `TARGET_QUEUED_FRAMES` (o alvo precisa ficar acima do tamanho do bloco). Migrar pra `AudioWorkletNode` (thread de áudio própria) resolveria de vez, mas precisa de arquivo de worklet separado — ver comentário no código.
- **Testado com o código real** no navegador (mock de `window.sinalElectron`): 300ms de áudio empurrados de uma vez → o código cortou os 160ms mais antigos e tocou só os 140ms mais recentes, exatamente o previsto. Não testado ainda numa call real (depende de alguém compartilhar pelo app desktop com áudio ligado).
- Só `public/app.js` — vai pelo Vercel, não precisa de instalador novo.

**Vídeo "farinhado" (pixelado/granulado) — ainda sem causa confirmada.** Três suspeitos, cada um com correção diferente: (1) o PC de quem compartilha reduzindo qualidade/resolução sozinho por CPU (codificar 1080p30 com jogo rodando) ou upload; (2) a VM `E2.1.Micro` (1/8 de núcleo) sem dar conta de repassar 6 Mbps pra cada espectador; (3) o espectador recebendo a camada baixa do simulcast do LiveKit (padrão pra tela: metade da resolução a 3fps, escolhida quando o tile fica menor que ~960px de largura por causa do `adaptiveStream: true`). Primeiro dado real (print do usuário): perda 0% e jitter 1ms do lado de quem assiste — rede limpa, enfraquece a hipótese (2) pelo menos desse lado.

**Diagnóstico adicionado, em vez de chutar**: o tooltip da bolinha de qualidade de cada tile (`sampleTileDetailedStats()`) agora mostra também **resolução recebida, fps e kbps** (a taxa precisa de duas amostras, então aparece a partir da segunda, ~4s depois). Como ler: 960×540 a ~3fps → camada baixa do simulcast (3); 1920×1080 com kbps baixo → banda/servidor (2); resolução menor com fps normal → PC de quem compartilha reduzindo sozinho (1). Próximo passo: passar o mouse no tile do amigo numa call real e decidir a correção pelos números.

**✅ Causa do vídeo "farinhado" achada com o diagnóstico (mesmo dia)**: tooltip no tile do amigo mostrou **`960×540 · 4fps · 10 kbps · perda: 0.0% · jitter: 1ms`** — hipótese (3), camada baixa do simulcast. A camada baixa padrão do LiveKit pra tela é metade da resolução a ~3fps, e o servidor escolhe a camada pela **altura do tile com 10% de tolerância**: o tile tinha ~577px de altura, e com a tolerância a camada de 540px já "servia" — mesmo com o tile grande na tela. (Os 10 kbps são só consequência: 3fps de uma tela quase parada comprime pra quase nada.)

**Corrigido**: `simulcast: false` nas opções de publicação da tela (`setScreenShareEnabled`, 3º argumento, junto do `screenShareEncoding`) — uma camada só, 1080p pra todo mundo. Bônus: quem compartilha codifica uma versão em vez de duas (menos CPU com jogo rodando). **Contrapartida aceita**: quem assiste sempre baixa a versão cheia (até 6 Mbps por tela aberta), sem opção mais leve — ok pro tamanho do grupo, e o clique-pra-assistir já evita baixar tela que ninguém tá vendo. Câmera continua com simulcast normal. Testado que a opção chega na chamada do LiveKit (sala falsa capturando os argumentos). **Precisa confirmar numa call real**: o tooltip do tile de quem compartilha deve passar a mostrar 1920×1080 (o fps pode aparecer baixo com tela parada — captura de tela só manda quadro quando algo muda, isso é normal). Só vale quando **quem compartilha** estiver na versão nova do site.

**Bolinha de qualidade presa em "Medindo conexão..." (cinza) — corrigido junto**: `RoomEvent.ConnectionQualityChanged` só dispara quando a qualidade **muda**. Com o clique-pra-assistir (§18), o tile nasce bem depois (só quando alguém clica pra assistir) — se a conexão da pessoa tava estável desde antes, o evento não vinha nunca mais pro tile novo. E quando a pessoa parava e recomeçava o compartilhamento, `handleTrackRemoved()` apagava o rótulo guardado, com o mesmo resultado. Corrigido em `handleTrackAdded()`: logo depois de criar o tile de vídeo, chama `updateQualityDot(participant.identity, participant.connectionQuality)` pra puxar o valor atual. **Segundo bug na mesma função**: `updateQualityDot()` só tratava `Poor`/`Good` e jogava todo o resto no verde "Boa conexão" — inclusive `Lost` (conexão perdida, o oposto) e `Unknown` (sem dado ainda). Agora são os 5 estados do enum do LiveKit 2.22.3: `excellent` verde, `good` amarelo "razoável", `poor` vermelho, `lost` vermelho "Conexão perdida", `unknown` cinza "Medindo conexão...". Testado no navegador com tile falso criado depois da conexão já estável (nasce verde na hora) e os 5 estados um por um.

**Diagnóstico do lado de quem compartilha (mesma leva)**: com simulcast desligado, o gargalo que sobra pra imagem ruim é o PC ou o upload de quem compartilha — e o navegador reduz resolução/fps/qualidade sozinho quando isso acontece, sem avisar ninguém. `sampleOwnScreenStats()` (roda no mesmo `setInterval` de 4s do diagnóstico de quem assiste) lê o `outbound-rtp` da tela e o `qualityLimitationReason` (`none`/`cpu`/`bandwidth`/`other`):
- Bolinha própria (`.send-dot`) só no **seu** tile de tela — classe separada da `.quality-dot` de propósito, senão o `ConnectionQualityChanged` do participante local sobrescreveria a cor. Verde = sem redução; amarela = reduzindo. Tooltip: `Enviando: 1920×1080 · 30fps · 4800 kbps · sem redução de qualidade` (ou `· reduzindo qualidade: CPU do seu PC sobrecarregada` / `upload insuficiente`).
- Quando há limitação, o status embaixo do seu nome vira `Transmitindo · limitado pela CPU` (ou `pelo upload`) — visível sem passar o mouse.
- Guarda contra corrida: se parar de compartilhar enquanto uma amostra tá pendente, ela não sobrescreve o "Assistindo" do `resetShareButton()`.
- Testado no navegador com sala/track falsos: tile próprio de tela tem a bolinha nova (câmera não; remoto continua com a de conexão), amostra sem limitação fica verde, amostra com `cpu` fica amarela com o status e a taxa certos, e a corrida ao parar mantém "Assistindo".

**Como usar pra diagnosticar**: quem compartilha olha o próprio status/bolinha; quem assiste passa o mouse no tile de quem compartilha. Juntos: se quem assiste recebe 1920×1080 limpo e quem envia não mostra limitação, tá tudo certo; se quem envia mostra "limitado pela CPU", a saída é o preset 720p (menos pra codificar); "pelo upload", idem ou melhorar a conexão; se quem envia tá limpo mas quem assiste recebe pouco kbps/perda, aí é rede/servidor.

**✅ Confirmado numa call real (2026-09-29)**: depois da v0.8.45 publicada, o usuário relatou transmissão visivelmente melhor e o tooltip mostrando a resolução cheia certinho. O vídeo "farinhado" era mesmo a camada baixa do simulcast, e desligar o simulcast na tela resolveu. Ainda pendente de confirmação real: o atraso do áudio isolado (precisa de alguém compartilhando pelo app desktop com áudio ligado, na versão nova) e o comportamento da VM com várias telas em 1080p ao mesmo tempo por bastante tempo.

## 31. Swap na VM + painel de consumo da VM (local) — 2026-09-29

**Swap (feito direto na VM, a pedido do usuário, depois de explicar o passo a passo)**: a VM não tinha swap nenhum — com 954MB de RAM (~446MB disponíveis), se a memória acabasse numa call cheia, o OOM killer do Linux mataria o processo mais pesado (o LiveKit) e a call cairia na hora. Criado `/swapfile` de 1GB (`fallocate` + `chmod 600` + `mkswap` + `swapon`), persistido no `/etc/fstab` (backup em `/etc/fstab.bak-sinal-swap`), e `vm.swappiness=10` em `/etc/sysctl.d/99-sinal-swap.conf` — só usa swap sob pressão real de memória (o padrão 60 jogaria coisa pro disco mesmo com RAM sobrando, adicionando latência à toa). Continua 100% Always Free: o arquivo fica dentro do volume de boot que já existia (46,6GB, dentro dos 200GB grátis) — nenhum recurso novo na Oracle. Shape confirmada via metadata da própria instância: `VM.Standard.E2.1.Micro`, `sa-saopaulo-1`. Desfazer: `sudo swapoff /swapfile`, remover a linha do `fstab`, o arquivo e o `99-sinal-swap.conf`.

**Painel de consumo da VM** (`tools/vm-dashboard/`, detalhes no `README.md` de lá): decisão do usuário de ser **local** (segurança — nada exposto na internet) mas **com histórico completo** (modelo "misto"):
- Na VM, serviço `sinal-stats` (`/opt/sinal-stats/collector.py`, Python puro, só leitura de `/proc`, cgroups v2 dos containers e da API do LiveKit em `127.0.0.1:7880` com JWT assinado com a chave do `livekit.yaml`). **Não abre porta nenhuma.** Grava média+pico a cada 10s (3 dias) e a cada 1min (30 dias) em `/var/lib/sinal-stats/`, e a leitura mais recente em `/run/sinal-stats/live.json`. Tetos rígidos no systemd (`MemoryMax=40M`, `CPUQuota=5%`, `ProtectSystem=strict`). **Custo medido de verdade**: ~14MB de RAM, ~0,16% de um núcleo, ~33MB de disco com histórico cheio. Contagens do LiveKit são só números (salas ativas, pessoas, telas, câmeras) — nunca nomes/identidades, decisão explícita.
- No PC: `npm run vm` sobe `tools/vm-dashboard/server.mjs` em `127.0.0.1:4173` — histórico via `ssh ... python3 /opt/sinal-stats/query.py <span> <pontos>` (já reduzido na VM, pico preservado) e ao vivo via uma única conexão SSH compartilhada (`cat live.json` a cada 2s), que só existe enquanto tem aba aberta. Página sem dependência externa (canvas puro), tema do Sinal, 1h/24h/7d/30d, tooltip, pico por gráfico. Vercel não publica (`outputDirectory: public`).
- **Acesso**: `SINAL_VM_KEY` (caminho da chave) e `SINAL_VM_HOST` ficam no `.env` local, **nunca no código** — o repo é público (malha fina feita antes do commit). O host é o mesmo domínio do LiveKit (§12; o IP efêmero antigo citado lá foi trocado pelo fixo). O nome do domínio foi adicionado ao `known_hosts` local depois de conferir que a chave do servidor é a mesma já confiada pro IP fixo.
- **Permissão do Claude Code**: o usuário liberou `ssh`/`scp` com essa chave em `.claude/settings.local.json` (o modo automático bloqueava acesso à VM de produção). Ainda assim, mudança na VM só depois de explicar e ter o ok.
- **Leitura importante do painel**: a E2.1.Micro tem só uma fração de núcleo — o número que mostra o teto é o **steal** (tempo que a Oracle segura a nossa CPU). Uso + steal subindo juntos sob carga = limite da máquina. Aberto o painel, a VM fica em ~0,5–1% de CPU; o pico de ~13% no gráfico ao abrir é o handshake do SSH.
- Próximo uso natural: o teste de carga (§ conversa sobre 60fps) — várias abas publicando vídeo sintético pesado, olhando CPU/steal/pps no painel.

## 32. Qualidades Leve / Nítido / Fluido + H.265 com reserva VP8 (2026-09-29, site v0.8.48, desktop v0.3.10)

**Por quê**: o usuário queria 60fps e imagem melhor, e achou o toggle HD/720p "meio paia". Teste de carga (§31) mostrou que a VM (E2.1.Micro) fica limpa até ~40 Mbps saindo e começa a apertar (steal 2%→30%) perto de ~76 Mbps — 2 telas 60fps em VP8 (~10 Mbps cada, vistas por 4) passariam disso ("duas transmissões e já peida? não dá" — usuário). Solução: codec mais eficiente.

**Medições que decidiram o codec** (página de loopback local no Brave do usuário, RX 7000, tela real com vídeo 60fps): VP8 e VP9 codificam na CPU (~5–7ms/quadro); **AV1 também na CPU** (libaom, 15ms/quadro — o Chromium não usa o AV1 por hardware da placa) → descartado; H.264 e **H.265 por hardware** (AMD via MediaFoundation). H.265 a 60fps usou ~4,3 Mbps onde VP8 60 usou ~7,8 → escolhido. Receptores decodificam VP9/H.264/H.265 por hardware.

**Presets** (`SHARE_QUALITY_PRESETS` em `public/app.js`): Leve 720p30 (H.265 2 Mbps / VP8 2,5), **Nítido** 1080p30 padrão (H.265 4 / VP8 6), Fluido 1080p60 (H.265 6; só com H.265 — reserva VP8 a 30fps 6 Mbps). Conta na VM (2 telas × 4 espectadores): Nítido ~32 Mbps, Fluido ~48 Mbps (= carga do Nítido VP8 antigo, zona limpa). `contentHint` motion + `maintain-framerate` no Fluido; detail + `maintain-resolution` nos outros.

**Codec**: `LivekitClient.supportsH265()` (o Chrome só lista H.265 nos codecs de envio quando há codificador por hardware) → `videoCodec:'h265'` + `backupCodec:{codec:'vp8'}` + `backupCodecPolicy: SIMULCAST`. Sem H.265 → VP8 puro (igual antes). **Testado ponta a ponta pela VM de produção** (vercel dev + abas, uma com H.265 removido das capacidades/SDP pra simular quem não suporta):
- Política padrão (PREFER_REGRESSION) era ruim: entrou alguém sem H.265 → **todo mundo** caiu pra VP8 e não voltava até recompartilhar. Com **SIMULCAST**: quem tem H.265 continua em H.265, quem não tem recebe VP8; quando essa pessoa sai, o VP8 desliga sozinho (dynacast); se só tem quem precisa de VP8 assistindo, o H.265 fica desligado.
- **Bug/limitação do livekit-client 2.22.3**: pra fonte de tela, a `encoding` do codec reserva é ignorada (usa o `screenShareEncoding` do principal) — no Fluido o VP8 reserva saía a 60fps/6 Mbps na CPU. Contornado em `capBackupCodec()` (roda na checagem de 4s das estatísticas): ajusta `sender.setParameters` + `track.simulcastCodecs.get('vp8').encodings` pro teto do preset. Verificado: reserva cai pra 30fps. Se atualizar o livekit-client, conferir se ainda precisa.

**Onde escolher**:
- **Site**: o antigo botão HD virou um botão com a qualidade atual (`720p`/`1080p`/`60fps` ▴) que abre um menu (`#qualityMenu`, pra cima). Fluido **cinza e desabilitado** (não some — pedido do usuário) com tooltip explicando quando não há H.265. ## 35. Trocar a qualidade no meio da transmissão (2026-10-02, site v0.8.50, desktop v0.3.12)

**Pedido do usuário** (roadmap §33 item 6, desenho aprovado antes): trocar entre Leve/Nítido/Fluido sem parar a transmissão.

**Por que não precisa republicar**: as três qualidades usam o mesmo codec (H.265 se o PC tem, senão VP8 — e Fluido só existe com H.265), então a troca é só captura + limites de envio, sem piscar pra quem assiste (mesmo `trackSid`, confirmado).

**Implementação** (`public/app.js`):
- `toggleShare()` agora **sempre captura no teto** (`effectiveShareQuality('fluido')` = 1080p60 com H.265, 1080p30 sem) e reduz na hora com `applyCaptureQuality()` (`applyConstraints` só com `max` + `contentHint`). Sem isso, subir de qualidade depois (Leve→Nítido) podia não funcionar.
- `changeActiveShareQuality(q)`: captura → `sender.setParameters` (maxBitrate/maxFramerate do preset no codec ativo, `activeShareCodec` guardado ao publicar) → `track.setDegradationPreference` → atualiza também `track.encodings` (o LiveKit reaplica isso quando alguém começa/para de assistir) e `track.publishOptions.screenShareEncoding`/`backupCodec.encoding` (de onde ele recalcula se a fonte for trocada — `refreshSenderEncodings`) → `capBackupCodec()` acompanha o `activeShareQuality` novo.
- **Bug achado no teste e corrigido**: chamar `setDegradationPreference` (assíncrono, também faz get/setParameters no mesmo sender) junto com o nosso `setParameters` dava `InvalidStateError: getParameters() has never been called` — a troca ficava só na captura (60fps capturado, envio ainda 30fps/4 Mbps). Agora é sequencial (nosso setParameters primeiro, com 1 nova tentativa com leitura fresca; depois o do LiveKit, aguardado).

**Também na v0.3.12 — app aberto sem internet** (relato do usuário: "abre só com uma tela preta e só muda se você encerrar o processo"): o `did-fail-load` só fechava o splash e mostrava a janela vazia, sem nunca tentar de novo. Agora (`main.js`): falha de carregamento do site (frame principal, URL do Sinal, ignorando -3/navegação cancelada) → `showOfflinePage()` carrega `src/offline.html` (tela própria, mesma linguagem do splash, sem fonte externa) e agenda novas tentativas com **espera que dobra a cada falha** (5s → 10s → 20s → 40s → 60s, teto de 60s — pedido do usuário; a tela mostra "Tentando novamente em Ns" via `sinal:offline-next-retry`/`onOfflineNextRetry`; "Tentar agora" e o evento `online` tentam na hora e, se falharem, só reiniciam a contagem sem aumentar a espera); `tryReconnect()` só navega de volta quando um `HEAD` no site responde (navegar às cegas faria a tela piscar a cada falha) e volta pra **mesma URL que falhou** (ex: link de convite `?sala=`). Botão "Tentar agora" e o evento `online` do Windows chamam `retryConnection` (preload) na hora. `did-finish-load` do site desliga o timer. **Não testado no Electron de verdade** — validar: desconectar a internet, abrir o app → tela de sem conexão → reconectar → abre sozinho.

**Também na v0.8.50 — áudio de música e selo de qualidade** (pedidos do usuário, roadmap §33 itens 8 e 11):
- **Áudio da transmissão** (aba no site e áudio isolado no app) publicado com `screenAudioPublishOptions()`: `AudioPresets.musicHighQualityStereo` (128 kbps), `forceStereo:true`, `dtx:false`, `red:false`. Antes era o padrão do LiveKit: 48 kbps **mono** (ele só detecta estéreo sozinho no Safari — `channelCount` em `getSettings()`) com DTX ligado (corta "silêncio", pode picotar música baixa). Testado pela VM: sender a 128000, SDP com `stereo=1` e sem `usedtx`, receptor com `channels: 2`.
- **Selo de qualidade** (`.res-badge` no rótulo do tile, ex. "1080p60" em âmbar, "1080p", "720p"): sai das estatísticas reais — `frameHeight`/`framesPerSecond` do `inbound-rtp` pra quem assiste (`sampleTileDetailedStats`) e do `outbound-rtp` no próprio tile (`sampleOwnScreenStats`), atualizado a cada 4s. Se a rede/PC baixar a qualidade, o selo mostra. Testado: "1080p" no Nítido e virou "1080p60" quando quem transmitia trocou pra Fluido.

**Correção na v0.3.13 — tela de sem conexão presa** (achado pelo usuário testando a 0.3.12 de verdade: "fica infinitamente essas telas, mesmo depois de voltar a internet"). Causa: quando o site falha, o Chromium carrega uma **página de erro interna que ainda tem a URL do Sinal** e dispara `did-finish-load`; o listener "terminou de carregar uma página do Sinal → voltou a internet" chamava `stopOfflineRetry()` (`offlineActive=false`) e daí o temporizador e o "Tentar agora" eram ignorados pra sempre (texto preso em "Tentando reconectar…"/"Tentando agora…"). Correção: o modo sem conexão só termina quando `tryReconnect()` confirma que o site respondeu; o temporizador começa já em `showOfflinePage()` (`offlineNextRetryAt`) e a contagem é enviada quando `offline.html` termina de carregar (`isOfflinePageShown()`); se a janela sair da tela por outro caminho (link de convite que carregou), as tentativas param sem puxar a janela de volta.
- **Lição**: a 0.3.12 foi publicada com essa parte testada só com o app simulado no navegador — e quebrou. Agora existe teste no Electron real: `electron/test/offline-recovery-test.mjs` (modo dev com `SINAL_DEV_URL` — override que **só vale não empacotado** — apontando pra um servidor local desligado, liga o servidor e observa pela porta de depuração). Resultados: **auto** → tela com contagem desde o início, voltou sozinho 0,5s depois do servidor responder; **manual** → servidor voltou faltando 8s pra próxima tentativa, "Tentar agora" voltou na hora. O servidor de teste tem que mandar `no-store` (`electron/test/nocache-server.mjs`) — com `python -m http.server` o cache heurístico do Chromium servia a página sem rede e dava falso negativo.
- O modo dev usa a **mesma pasta de dados do app instalado** (`%AppData%\sinal-desktop`) — depois do teste, limpar as origens de teste (`Storage.clearDataForOrigin` via CDP) foi feito.
- Release: depois de publicar, o "Procurar atualização" leva 1–2 min pra enxergar a versão nova (feed de releases do GitHub) — normal, observado na 0.3.12.

## 36. PLANO — Servers no Sinal (estilo Discord) — pesquisado em 2026-10-02 (Fase 1 implementada, ver §38)

**Pedido do usuário** (resumo fiel): servers tipo Discord; "a pessoa abre a live no server e outros membros simplesmente entram na call por lá"; os servers do Sinal **são os servers do Discord**, mas **a pessoa escolhe quais aparecem** (exige Discord); cada server tem espaço pra **criar salas** (podem ser lives soltas), **bem organizado, estilo a lista de calls de voz do Discord** (avatar de quem está, nome da sala…); **salas privadas** onde quem cria é admin e **aprova a entrada ou pede senha**; **cuidado com o problema de sucessão de host** (saída em massa e o admin não passa direito); e **tirar o webhook** de "fulano abriu uma sala".

### Pesquisa (fontes primárias)
- **Discord** `GET /users/@me/guilds` (escopo OAuth `guilds`): até **200 servers numa chamada** (máximo que um usuário pode ter — paginação desnecessária); campos `id, name, icon, owner, permissions` (bitfield do usuário naquele server: `ADMINISTRATOR`=0x8, `MANAGE_GUILD`=0x20). `guilds.members.read` daria o apelido/avatar no server (opcional). OAuth `prompt=none` pula a tela de consentimento se já autorizado (renovar a lista de servers sem fricção). Token do Discord dura 7 dias. Ícone: `https://cdn.discordapp.com/icons/<id>/<hash>.png` (CSP `img-src` já libera `cdn.discordapp.com`).
- **LiveKit** (server SDK 2.19.1 instalado; servidor 1.13.6): `createRoom({ metadata, maxParticipants, emptyTimeout, departureTimeout })`, `updateRoomMetadata`, `listParticipants` (traz `joined_at`), **`updateParticipant(room, id, { permission, metadata, attributes })` — mudar permissão vale na hora e o servidor revoga o token antigo**, `removeParticipant(room, id, { revokeTokenTs })` (expulsar sem volta com token velho), `sendData(room, data, kind, { destinationIdentities, topic })`. Cliente: `RoomEvent.ParticipantPermissionsChanged`/`ParticipantMetadataChanged`/`RoomMetadataChanged`, `participant.joinedAt`.
- **Vercel Hobby**: **1.000.000 invocações/mês** e **4 h de Active CPU/mês** (espera de rede não conta). Medido: uma consulta de "salas ao vivo" (HMAC + listRooms + listParticipants + JSON) gasta **< ~5 ms de CPU aquecida**, 30–45 ms a frio, ~120 ms de relógio.
- **Sucessão de host**: o bug citado é da era PeerJS (v0.5–0.7, §5/§11): um navegador "segurava" a sala e os outros elegiam outro quando ele saía — frágil, quebrava em saída em massa. Desde o LiveKit (v0.8.0) não existe dono; **o plano NÃO reintroduz eleição no cliente**.

### Arquitetura proposta (continua SEM banco de dados)
1. **Sessão assinada** (substitui `discord_name`/`discord_avatar` em query string e o `adminProof` separado): o `discord-callback` pede `identify guilds`, busca perfil + servers e devolve um **token assinado (HMAC, mesmo esquema do `lib/adminProof.js`)** com `{ id, name, avatar, admin, guilds:[{id,name,icon,manage}], exp: 7 dias }` — no **fragmento** da URL (`#session=…`, não vai pra servidor/log/Referer), guardado no `localStorage`, mandado no corpo dos POSTs. Expirou → renovação silenciosa (`prompt=none`). Quem é membro de qual server quem diz é o Discord, no login.
2. **Servers escolhidos**: lista local (por dispositivo) de quais servers do Discord aparecem — só interface; o servidor sempre cruza com os servers da sessão.
3. **Sala de server** = sala do LiveKit `s<guildId>-<6 aleatórios>` com **metadados** `{ v:1, guild, title, creator:{id,name}, access:'open'|'password'|'approval', pw?:HMAC(segredo, sala+senha), createdAt }`. Some sozinha quando esvazia (lives soltas). Limite de salas ao vivo por server (ex: 10) e `maxParticipants`.
4. **`api/get-token`** ganha o modo server: confere sessão + membro do server da sala + regra de acesso (aberta / senha confere / ticket de aprovação válido); identidade `d<discordId>-<4 aleatórios>` com `discordId`/nome/avatar **assinados pelo servidor** nos atributos do participante.
5. **`api/lives`** (POST, sessão + servers escolhidos): `listRooms` → filtra metadados dos servers permitidos e sala com gente (ou criada há < 30 s — o LiveKit às vezes demora a apagar sala vazia, §5.1) → `listParticipants` de cada → devolve por server: salas (nome, cadeado, quem está: avatar/nome/transmitindo/câmera). Senha e ids internos nunca saem.
6. **Atualização da lista**: a cada **15 s com a tela de servers visível**, 60 s dentro de uma call (bolinha dos outros servers), **para** com a janela escondida. Conta: 8 pessoas × 5 h/dia → ~290 mil chamadas/mês (29% do limite) e ~50 min de CPU (≈20% das 4 h). Se o grupo crescer: push (sala de presença por server no próprio LiveKit + `sendData`) — próximo passo, não necessário agora.
7. **Webhook sai**: bloco do `DISCORD_WEBHOOK_URL` em `get-token.js` removido; a variável pode ser apagada na Vercel.

### Salas privadas e o "responsável" (sem sucessão no cliente)
- **Com senha**: o servidor confere contra o HMAC dos metadados (segredo do servidor — quem está na sala vê os metadados mas não quebra sem o segredo). Não depende de ninguém online.
- **Com aprovação**: quem pede entra numa **sala de espera** (`<sala>~espera`) **sem permissão de ver/ouvir/publicar nada** (não vê a sala nem o chat); o servidor avisa a sala privada (`sendData`, topic `knock`). O responsável clica **Aprovar** → `api/room-admin` confere quem pede (token LiveKit + regra abaixo, com a lista **oficial** do servidor) → `updateParticipant` na espera grava um **ticket assinado (2 min)** no metadado do pedinte → o app dele recebe na hora, pede o token real com o ticket e entra. **Recusar** = `removeParticipant` da espera. Pendentes também listáveis pela API (quem entrou depois/recarregou não perde a fila).
- **Responsável (regra derivada, nunca "passada")**: (1) o **criador**, se estiver na sala; senão (2) quem **entrou primeiro** entre os presentes (`joined_at` do servidor); e **sempre** (3) quem tem `MANAGE_GUILD`/admin/dono **no server do Discord**. O servidor recalcula a cada ação → **saída em massa não quebra nada**: não há transferência a perder; quem sobrou e entrou primeiro já é o responsável; se todos saem, a sala some. O app mostra a coroa pela mesma regra (só visual). Criador volta → volta a ser o responsável.
- Ações do responsável: aprovar/recusar, expulsar (`revokeTokenTs`), renomear, fechar (`deleteRoom`), trocar senha.

### Interface (estilo Discord)
- **Trilho à esquerda**: "Início" (sala rápida por código — continua pra quem não usa Discord / chamar alguém de fora) + ícones dos servers escolhidos (redondos, **bolinha vermelha** se tem gente ao vivo) + "+" pra escolher servers.
- **Coluna do server**: nome; seção **SALAS** com **"+" criar sala** (nome, tipo: aberta / senha / aprovação); cada sala como canal de voz: 🔊/🔒 + nome, embaixo os participantes (avatar + nome + ícone de tela/câmera + "AO VIVO" + selo de qualidade). Clicar = entrar (ou pedir/senha).
- **Área principal**: a sala atual (palco, como hoje). A coluna continua visível na call pra pular de sala.
- Celular: trilho e coluna viram gaveta.

### Fases
1. **Base (sem mudança visível)**: sessão assinada + `guilds`, renovação silenciosa, `get-token` modo server, `api/lives`, remover webhook, testes unitários (assinatura, nome de sala, regra do responsável).
2. **Interface**: trilho, escolher servers, coluna com salas ao vivo, criar sala aberta, entrar, atualização periódica, bolinha.
3. **Privadas**: senha, aprovação (espera + ticket), responsável derivado, ações, poderes de admin do Discord.
4. **Polimento**: links `sinal://` pra sala de server, Novidades, opcional presença "online no server" (push via LiveKit).
- **Teste sem Discord real**: sessões de teste assinadas com o segredo do `.env` (usuários/servers falsos) + várias abas pelo `vercel dev` contra o LiveKit real. O login real com Discord, o usuário testa no fim.

### Decisões do usuário (2026-10-02, respondidas antes de codar)
1. **Login no app desktop pelo navegador padrão** voltando pelo `sinal://` ("como as empresas grandes fazem, tipo Riot Client"). Desenho: o app gera um **nonce aleatório**, abre o navegador em `/api/discord-login?client=app&nonce=…`; o callback mostra "Voltando pro Sinal…" e redireciona pra `sinal://auth#session=…&nonce=…`; o Electron (`second-instance`/argv) repassa ao site, que **só aceita a sessão se o nonce for o que ele mesmo gerou** (impede outro programa de injetar login). No site (navegador) o login continua na mesma aba, sessão no fragmento `#session=`.
2. **Sala privada mostra quem está dentro, com cadeado** ao lado do nome.
3. Dois papéis distintos: **admin do Sinal** (o usuário — `ADMIN_DISCORD_IDS`, a coroa de hoje) **entra em qualquer sala sem senha/aprovação e modera** — em qualquer server do Discord de que ele faça parte (os outros nem aparecem pra ele). **Admin/dono de cada server do Discord** (`MANAGE_GUILD`/`ADMINISTRATOR`/owner): proposta = modera as salas do próprio server (expulsar, fechar) mas **pede pra entrar** em sala privada como qualquer um — **aguardando confirmação do usuário**.
4. **10 salas ao vivo por server.** Pessoas por sala: hoje não há limite (LiveKit padrão = ilimitado); o limite real é a VM (12 assistindo 1 tela Fluido ≈ 66 Mbps, perto do aperto do teste de carga). Proposta: teto alto anti-abuso (25), sem travar em 12; painel da VM vigia.
5. **Servers escolhidos por dispositivo** por enquanto. Sincronizar site × app exigiria guardar preferência no servidor (banco) — **evolução futura planejada com calma**; a identidade já vira o ID do Discord neste plano, faltaria só o armazenamento (ex: Redis que já roda na VM, atrás de uma API).

## 37. Registro do app, recuperação automática e "Enviar relatório" (2026-10-03, site v0.8.51, desktop v0.3.13)

**Motivo:** o usuário relatou crash no Valorant com transmissão em Fluido (janela). Investigação: o LiveKit mostrou `PEER_CONNECTION_DISCONNECTED` ~20 s depois do cliente silenciar (a VM estava normal), e o log do Windows não tinha TDR de vídeo nem crash do Sinal — não havia nenhum dump porque nada registrava. Causa exata desconhecida (60 fps × captura de janela × áudio isolado). Pedido: registro do app, recuperação sozinha e um jeito de a pessoa mandar o relatório direto, sem abrir pasta.

### O que existe
- **Registro do app** (`electron/src/main.js`): arquivo `logs/sinal.log` dentro da pasta de dados do app (gira em 1 MB → `sinal.old.log`). `console.log/warn/error` do main também vão pro arquivo; o renderer manda linhas via `sinalElectron.log()` (início/fim/troca de qualidade de transmissão com a superfície capturada, entrada em sala, etc.) e `console-message` capta avisos/erros que começam com `[sinal`. Registra também `render-process-gone`, `child-process-gone`, `unresponsive/responsive`, versão e GPU no começo. `crashReporter.start({ uploadToServer: false })` — dumps só ficam locais.
- **Privacidade do registro**: `readLogTail()` troca a pasta pessoal e o usuário do Windows por marcadores antes de entregar; nada de conteúdo de sala, conversa ou tela.
- **Recuperação automática**: `recoverMainWindow()` recarrega a janela 0,8 s depois de um `render-process-gone`. Se a pessoa estava numa sala (`setInRoom(true, codigo)` guarda `lastRoomCode`), volta com `?sala=CODIGO&retomar=1`; o site (`resumeAfterAppRecovery()` em `app.js`) entra sozinho se já houver nome salvo. **Só na primeira falha em 5 min** volta pra sala — repetida, só recarrega (evita laço de crash).
- **Enviar relatório**: Configurações → "Problemas" → diálogo com descrição opcional, "Ver o que vai junto" (mostra o registro inteiro) e Enviar → `POST /api/report` (`api/report.js`) → webhook de um **canal privado** do Discord (mensagem + `.txt` anexo, `allowed_mentions` vazio). Limites: descrição 1500 chars, registro 80 KB, 3 envios/10 min por IP (em memória da instância — melhor esforço), 503 se a variável não existir, 502 se o Discord recusar.
- **Variável na Vercel:** `DISCORD_REPORT_WEBHOOK_URL` (produção/preview como *Sensitive*; development normal). **Nunca** colocar a URL em arquivo versionado, issue ou PR. Se vazar/for abusada: apagar o webhook no Discord e criar outro, depois `vercel env rm` + `vercel env add`.
- A seção só aparece no app desktop ≥ 0.3.13 (precisa de `sinalElectron.getLogTail`).

### Testado
- `api/report.js` contra um webhook falso local: mensagem + anexo OK, `@everyone` neutralizado, 4º envio → 429, vazio → 400, > 80 KB → 413, sem variável → 503.
- Diálogo no navegador (DOM): seção visível, abre, prévia mostra o registro.

### Ideias futuras
- Tentar Fluido com tela inteira em vez de janela pra isolar o gatilho do crash do Valorant; se o relatório mostrar `render-process-gone` com `reason` de GPU, considerar desligar aceleração de GPU no app como opção.

## 38. Servers — FASE 1 (base) implementada (2026-10-03, site v0.8.52)

Executa a "Fase 1" do plano do §36. **Sem mudança visível** além do login: a interface (trilho, coluna de salas) é a Fase 2.

### Decisões novas do usuário (2026-10-03)
- **Todo mundo é deslogado** (sem compatibilidade com o formato antigo): ao abrir o site, `sinal:discordUser` é apagado e aparece "Atualizamos o login com o Discord — entre de novo pra liberar os servers". O Discord pede o escopo extra `guilds` na nova autorização.
- **Moderação por patente no server:** dono, Administrador e Gerenciar Servidor **moderam** as salas do próprio server; **só dono e Administrador entram em sala privada** sem pedir/senha ("cargos de patente mais alta"). Gerenciar Servidor modera mas pede pra entrar em privada. O admin do Sinal (`ADMIN_DISCORD_IDS`) entra em qualquer sala dos servers de que faz parte. (Interpretação minha de "patente": o Discord só expõe permissões no OAuth, não a hierarquia de cargos; se o usuário quiser outra regra, é só `canEnterPrivate` em `lib/rooms.js`.)
- **Login pelo navegador padrão no app desktop (`sinal://`)** fica pra Fase 2 ("na fase de utilização"); até lá o app usa o login atual (navega na própria janela e volta com `#session=`).

### O que foi feito
- **`lib/session.js`** (substitui `lib/adminProof.js`, removido): sessão `{ v:1, id, name, avatar, admin, guilds:[[id,nome,icone,nivel]], exp }` assinada com HMAC-SHA256; chave **derivada** do `DISCORD_CLIENT_SECRET` com rótulo de domínio (não precisou de variável nova; trocar o secret desloga todo mundo). Validade **7 dias** (igual ao token do Discord). Níveis: `o` dono, `a` Administrador (0x8), `m` Gerenciar Servidor (0x20), `x` membro. Limite de ~7000 caracteres pro redirect: se passar (Discord permite 200 servers), ficam os de mais poder e corta o resto.
- **`api/discord-login.js`**: escopo `identify guilds`. **`api/discord-callback.js`**: busca perfil + `/users/@me/guilds`, monta a sessão e redireciona pra `/?sala=…#session=<token>` — **fragmento**, não query (não vai pra servidor/log/Referer). Se a lista de servers falhar, o login segue sem servers. O token do Discord é descartado.
- **`api/get-token.js`** (reescrito): `session` no corpo (assinada) substitui `avatar`/`adminProof`. Sessão presente e inválida/vencida → **401 `sessao-invalida`** (o site limpa e pede login). Modos `join`/`create` (salas por código — visitante e logado) e **`server-join`/`server-create`**. Identity do logado: `d<discordId>-<rand>`; metadata `{ avatarUrl, isAdmin?, userId }` vem **da sessão**, nunca do corpo. `roomAdmin`: admin do Sinal em salas por código; em salas de server, `canModerate` (dono/Admin/Gerenciar + admin do Sinal). **Webhook "fulano abriu uma sala" removido** — a variável `DISCORD_WEBHOOK_URL` na Vercel já não é usada (pode apagar; deixei pro usuário decidir). Resposta agora traz também `room`.
- **Salas de server:** nome `s<guildId>-<6 minúsculas/números>` (sempre minúsculo, as por código são sempre MAIÚSCULAS → nunca colidem); criada com `emptyTimeout/departureTimeout: 60`, `maxParticipants: 25` e metadados `{ v:1, guild, title, creator:{id,name}, access:'open', createdAt }`. **Limite de 10 salas por server** (429 `limite-de-salas`). Título limpo (sem `< >` nem controle, 40 chars). Só `access:'open'` existe; o campo e a checagem de privada já estão no lugar pra Fase 3 (403 `sala-privada`).
- **`api/lives.js`** (novo): POST `{session, guilds:[ids]}` → só servers pedidos **∩** servers da sessão; por server, salas ao vivo (com gente, ou criadas há < 30 s) com `{room,title,access,creator,createdAt,participants:[{name,avatar,admin,screen,camera,joinedAt}]}`. Nunca devolve segredo (a senha das privadas, quando existir, é só um hash nos metadados e não sai daqui).
- **`lib/rooms.js`**: regras puras — `parseServerRoom`, `newServerRoomName`, `cleanTitle`, `buildRoomMetadata/parseRoomMetadata`, `canModerate`, `canEnterPrivate`, **`responsibleOf`** (criador se estiver, senão quem entrou primeiro; recalculado a cada ação, sem "passar" o cargo — a resposta pro problema de sucessão de host). `responsibleOf` ainda não é usado por nenhuma rota (entra na Fase 3).
- **Cliente (`public/app.js`)**: `discordUser = { id, name, avatar, admin, guilds:[{id,name,icon,tier}], exp, session }` guardado em `sinal:session`; `decodeSession` só LÊ o conteúdo (quem decide é o servidor); vencida/corrompida é descartada; `connectToRoom` manda `session` e trata 401. Os indicadores de admin passaram de `adminProof` pra `discordUser.admin` (cosméticos; o poder é conferido no servidor).

### Testado

No navegador: login antigo apagado com a mensagem, `#session=` salvo e limpo da URL, nome preenchido, criar sala por código logado funciona.

### Fase 2c — login pelo navegador padrão no app desktop (feita no código, desktop v0.3.14)
Decisão do usuário (§36): como "as empresas grandes" (Riot Client etc.): o app abre o **navegador padrão** (onde a pessoa já costuma estar logada no Discord) e volta sozinho pelo `sinal://`. Antes o login navegava dentro da própria janela do app.
- **Fluxo:** (1) clicar em "Entrar com Discord" no app → `startAppLogin()` gera um **nonce** (16 bytes aleatórios, hex), guarda em `sinal:loginNonce` (uso único, vale 10 min) e chama `sinalElectron.openLogin(nonce)`; (2) o **main** monta a URL (`<site>/api/discord-login?client=app&nonce=…` — origem é sempre a do Sinal, o site só fornece o nonce; `electron/src/auth-url.js`) e abre com `shell.openExternal`; (3) `api/discord-login.js` aceita `client=app` só com nonce válido (32 hex, senão 400) e manda `state = app.<nonce>` pro Discord; (4) `api/discord-callback.js` reconhece o state, monta a mesma sessão assinada e redireciona pra **`/login-app.html#session=…&nonce=…`** (fragmento; falha → `#error=1`); (5) `public/login-app.html` + `login-app.js` (script em arquivo próprio por causa da CSP) valida o formato, limpa o fragmento do histórico e abre **`sinal://auth?session=…&nonce=…`** (+ botão "Abrir o Sinal" de reserva — o navegador pode perguntar se deixa abrir); (6) o Windows lança uma segunda instância → `second-instance` no main → `parseAuthUrl` (formato estrito, ≤ 12 KB) → `deliverAuth` mostra/foca a janela e manda `sinal:auth` ao site (se a página ainda estava carregando, fica em `pendingAuth` e o site pega com `takePendingAuth()`); (7) `consumeAppAuth()` só aceita se o **nonce for exatamente o guardado** (e < 10 min), consome o nonce, `decodeSession` e `applyNewLogin()` (sem recarregar: mostra "Conectado como…", trilho de servers, presença, abre o seletor na primeira vez).
- **Por que o nonce:** sem ele, qualquer página poderia disparar `sinal://auth?session=<sessão de OUTRA conta>` e fazer a vítima entrar logada como o atacante. A assinatura da sessão já impede forjar; o nonce impede "empurrar" uma sessão legítima alheia.
- **"Atualizar meus servidores" no app** também usa o navegador (`startAppLogin({refresh:true})` → `prompt=none`): a janela do app não tem cookie de login do Discord, então o `prompt=none` só funciona no navegador. Se o Discord recusar (sem login/consentimento no navegador), cai em `/login-app.html#error=1` com instrução de tentar de novo.
- **Compatibilidade:** app antigo (≤ 0.3.13) não tem `openLogin` → `hasAppLogin()` é falso e o site segue o caminho de antes (navega na mesma janela e volta com `#session=`). Navegador comum idem.
- **Segurança/limitações:** a sessão (credencial de 7 dias) passa pela linha de comando do `sinal://` por instantes — visível a outros processos **do mesmo usuário Windows**, que já leriam o `localStorage`; não vai pra log de servidor nem pro histórico do navegador (fragmento + `replaceState`). `SINAL_TEST_LOGIN_FILE` (só com o app **não** empacotado) faz o main gravar a URL num arquivo em vez de abrir o navegador — existe só pro teste.
- **Testes:** 85 no total — `tests/auth-url.test.mjs` (nonce, URL do app, parse estrito do `sinal://auth`), fluxo do app em `discord-callback.test.mjs` (state, 400 sem nonce, redirect pra `/login-app.html` com sessão+nonce no fragmento, falhas, state "parecido" tratado como sala comum), `newLoginNonce`. **No Electron real:** `electron/test/browser-login-test.mjs` (CDP + segunda instância; fechar o app instalado antes) **Resultado (2026-10-03, Electron 44.4.3 real, tudo OK):** o botão pede o login ao main com nonce e a URL abre no site certo com o mesmo nonce guardado; `sinal://auth` com nonce errado chega ao app e é recusado ("Não reconheci esse login…"); com o nonce certo loga ("Conectado como…", sessão salva, trilho de servers); repetir o mesmo link depois de deslogar não loga (nonce de uso único). **Armadilha ao escrever o teste:** com `spawn(..., {shell:true})` no Windows o `&` da URL vira separador de comandos do cmd e corta o `nonce` (o link "não chegava", e o caso do nonce errado passava de graça) — por isso a URL vai entre aspas e o teste agora também confere que o link recusado **chegou** ao app. O registro do protocolo no Windows (`Sinal.exe "sinal://…"`) já vem entre aspas. Ainda **não** testado de ponta a ponta: o OAuth real do Discord → `/login-app.html` → `sinal://` com o app instalado (só depois do deploy; o usuário testa).

### Tempo real (IMPLEMENTADO no código; falta só ligar o webhook na VM — ver "Go-live")
15 s de polling era lento e caro (8 pessoas × 5 h/dia ≈ 290 mil chamadas/mês; 5 s estouraria o limite de 1 M da Vercel). Agora: **LiveKit webhook → `/api/lk-webhook` → push por uma "sala de presença"**.
- **`api/lk-webhook.js`**: `WebhookReceiver` do SDK confere a assinatura (JWT do LiveKit no `Authorization`, com o sha256 do corpo) — sem assinatura válida, 401; depois de validado responde sempre 200 (erro nosso não pode gerar reenvio em loop). Só age em `room_started/finished`, `participant_joined/left`, `track_published/unpublished` de salas `s<guild>-…` (ignora salas por código e a própria sala `presence`). Monta a foto **daquele server** (`lib/lives.js`, a mesma de `api/lives.js`) e manda por `sendData` (RELIABLE, tópico `lives`) **só pros participantes de presença cujo atributo `guilds` inclui o server** — o atributo é assinado no token pelo `get-token`, o cliente não altera; ninguém recebe sala de server alheio. Em `participant_left`/`room_finished` o item do evento sai da foto (o webhook pode chegar antes da listagem refletir). Foto > 12 KB vira `{guild, refresh:true}` e o cliente busca em `api/lives`. Se ninguém ouve aquele server, nem monta a foto.
- **`get-token` modo `presence`**: exige sessão; devolve token da sala `presence` com `canSubscribe` mas **sem publicar nem enviar dados**; os servers (pedidos ∩ sessão, até 15) vão em `attributes.guilds`; não cria sala (entrar já cria a `presence`, que some quando esvazia).
- **Cliente (`app.js`)**: `startPresence()` abre a conexão leve (uma por pessoa, qualquer número de servers), `handlePresenceData` → `applyLives()` (só aceita servers escolhidos e salas bem formadas); cai → volta sozinha com espera 2/5/10/30 s e faz uma consulta ao reconectar (`Reconnected`/novo `connect`); trocar os servers no seletor reabre com o atributo novo; deslogar fecha. Com a presença conectada a consulta periódica cai pra **60 s** (rede de segurança); sem ela continua 15 s. A presença **não** para dentro da call (a 2b precisa dela).
- **Testes** (73): `lk-webhook.test.mjs` (assinatura, filtro de eventos/salas, entrega só pra quem ouve, saída/fechamento fora da foto, presença inexistente, foto grande), modo `presence` no `get-token.test.mjs` (atributo vem da sessão, não do corpo, sem publicar). **No LiveKit real via `vercel dev`:** presença conectou; webhook assinado de verdade (mesmo esquema do LiveKit, `AccessToken` + `sha256`) → a sala nova e depois o participante apareceram na tela **sem nenhuma consulta**; sem assinatura → 401; derrubar a presença → reconectou sozinha em ~2 s.

## 41. Moderação por hierarquia nos servidores (2026-10-03, site v0.8.55)

Pedido do usuário: admins de servidor moderam as salas do próprio servidor, **com prateleiras** — "um admin não pode expulsar um dono, e um dono não pode me expulsar".

**Hierarquia** (`moderationRank`/`canModerateTarget` em `lib/rooms.js`, espelhada no `app.js`): **admin do Sinal (0) > dono do servidor (1) > administrador (2) > "gerencia o servidor" (3) > membro/visitante**. Só se modera quem está **estritamente abaixo**: dois administradores não se expulsam, dois donos idem; o admin do Sinal modera qualquer um e **ninguém** o modera. O nível de cada pessoa vem de `metadata` do participante (`isAdmin`, `tier`, `guild`), gravado pelo `get-token` a partir da **sessão assinada** — o cliente não altera.

**Brecha que quase entrou e foi fechada:** o grant `roomAdmin` do LiveKit dá acesso à **API administrativa inteira** do LiveKit pro token (RemoveParticipant etc.) — quem o tivesse poderia pular a hierarquia chamando a API direto. Por isso **só o admin do Sinal recebe `roomAdmin`**. Dono/administrador/gerencia moderam por um **nível assinado no metadata do token** (`tier` + `guild`), conferido em `api/moderate.js` via `isModeratorToken()` (só vale na sala de servidor daquele mesmo guild; em sala por código só o admin do Sinal). **Provado no LiveKit real:** token de staff → **401** em `ListParticipants`/`RemoveParticipant` direto; token do admin do Sinal → alcança a API.

**`api/moderate.js`:** (1) `isModeratorToken` (grant ou nível+guild); (2) `listParticipants` → alvo inexistente = 404 `participante-nao-encontrado`; (3) `canModerateTarget(meta do chamador no token, meta do alvo)` → senão 403 `sem-permissao-sobre-alvo`. **Cliente** (`app.js`): `canModerateParticipant(p)` decide o botão "Expulsar" do roster e o menu "Desligar tela/câmera" dos tiles (antes só aparecia pra `discordUser.admin`); mensagens de erro humanas. Cosmético — o poder real é do servidor.

**Testes:** 102 no total — `tests/moderate.test.mjs` (matriz completa: admin do Sinal expulsa todos; dono não expulsa o admin do Sinal nem outro dono; administrador só gerente/comum; gerencia só comum; comum nada, mesmo com metadata mentindo; dono de outro servidor/sala por código; alvo que saiu; mute segue a hierarquia), `session-rooms` (ranking, hierarquia, `isModeratorToken`), `get-token` (staff **sem** roomAdmin, com `tier`/`guild`; admin do Sinal com roomAdmin). **Navegador + LiveKit real, 3 pessoas na mesma sala (dono, membro comum, admin do Sinal):** admin do Sinal vê "expulsar" em todos; dono vê só no membro comum (sem botão no admin do Sinal); membro comum não vê nenhum; o dono **forçando** `POST /api/moderate` contra o admin do Sinal levou 403 (ele continuou na sala) e expulsar o membro comum funcionou.

### Regressão do CSP × service worker (2026-10-04, site v0.8.57) — causada pela auditoria de segurança
- **Sintoma (relato do usuário, no app e no site):** depois de atualizar, o site só funcionava com **Ctrl+Shift+R**; num refresh normal ficava sem fontes (caía pra serifada), sem ícones/avatares do Discord e **sem conseguir criar nem entrar em sala** (só o login funcionava).
- **Causa:** `public/sw.js` intercepta TODO GET (`fetch(event.request)`), inclusive de outros domínios (Google Fonts, `cdn.discordapp.com`, o script do `livekit-client` no jsDelivr). O `fetch()` de um service worker é conferido pelo CSP **do próprio `sw.js`** (o `connect-src`), e o `connect-src` restrito de `vercel.json` (§42 S8: só o site + o host do LiveKit) passou a **bloquear** esses pedidos. Sem o script do LiveKit, `LivekitClient` fica indefinido e nada conecta. O Ctrl+Shift+R pula o service worker, por isso "consertava". Aparece só a partir da **segunda** visita (o service worker precisa ter assumido a página), por isso o teste de fumaça em perfil/aba limpa não pegou.
- **Correção:** o service worker agora só trata pedidos da **própria origem** (`new URL(request.url).origin === self.location.origin`); o resto vai direto pro navegador, sob o CSP da página. Sem cache e sem rede devolve `Response.error()` (antes `respondWith(undefined)`). **Reproduzido e verificado no navegador**: antes, `LivekitClient` indefinido + 0 fontes + avatar do Discord falhando; depois, LiveKit carregado, as 3 fontes, avatar ok e entrada em sala. `tests/service-worker.test.mjs` (5 testes) falha no `sw.js` antigo e passa no novo. **Quem estava "preso" no estado quebrado** sai sozinho: o navegador/app baixa o `sw.js` novo, ele assume na hora (`skipWaiting` + `claim`) e o refresh seguinte já vem bom (ou Ctrl+Shift+R na hora).
- **Lição:** ao restringir o CSP, testar com a página **sob o controle do service worker** (visitar, esperar, recarregar), não só na primeira visita. Mexer em `connect-src` afeta também o service worker.

### Ideia 2 (tiles maiores) — IMPLEMENTADA (2026-10-04, site v0.8.58)
- **Causa do tamanho pequeno** (medido no print do usuário, tela 1920×1060): (1) teto de **1440 px** de largura da página (sobravam ~480 px sem uso) e (2) a largura de cada destaque vinha de regra fixa de CSS (`repeat(auto-fit, minmax(460px, 1fr))` + `max-height:76vh`), então duas transmissões ficavam **712×400** com ~220 px vazios embaixo.
- **O que mudou:** (a) `body.in-room main, body.in-room header.top { max-width:none }` — **dentro da sala** a largura é total (a tela inicial continua centralizada em 1440 px); (b) **encaixe automático** — `bestSpotlightLayout(n, W, H, gap)` (pura, testada) escolhe, entre 1 coluna, 2 colunas…, o arranjo que dá o **maior tile 16:9** no espaço livre (empate fica com menos colunas; largura mínima 240 px) e `fitSpotlight()` grava `--spot-cols`/`--tile-w` na grade (mede o espaço livre com os destaques recolhidos e desconta a faixa de minimizados); roda via `scheduleFitSpotlight()` ao fixar/minimizar, ao redimensionar a janela e por `ResizeObserver` em `.room-main`/`#stageArea` (coluna de salas, painéis embaixo). **O agendamento usa `requestAnimationFrame` E um `setTimeout(120)` (o que vier primeiro)** — o navegador suspende `rAF` (e `resize`/`ResizeObserver`) com a janela oculta/minimizada; (c) **compactação só na sala** (`style.css`): paddings do corpo, margens do cabeçalho e da barra da sala menores e sem a frase "transmissão de tela ao vivo" — em janela de 720 px o palco passou de **283 → 345 px** de altura.
- **Medido no navegador (LiveKit real, 2 transmissões publicadas por participantes de apoio):** 1920×1060: **934×525 cada** (antes 712×400, +72% de área), sem rolagem; 1280×720: 614×345 (antes 503×283 sem a compactação), sem rolagem; janela 760×1000 (estreita/alta): **empilha** as duas, cada uma no maior tamanho que cabe. Com 1 destaque + 1 minimizado: 1432×806 em 1920×1060. 6 testes novos do cálculo (`pure-logic.test.mjs`; 140 no total).
- **Observação sobre o teste:** com a janela do pane **oculta**, o navegador só repinta (e dispara `resize`/RO) quando algo força a pintura — uma captura de tela resolve; na janela real isso acontece sozinho.
- **Não feito (ideias):** até 4 destaques (hoje o máximo continua 2) e um botão de layout (lado a lado / empilhado / uma grande + faixa).
